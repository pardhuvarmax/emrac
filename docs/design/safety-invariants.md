# Safety invariants

Safety rules are system invariants, not warnings: each one is a property the code keeps and a test that shows it under failure. This page is the register. It states what is **kept today**, what is **a known gap**, and where the gap is scheduled. It promises only what the implementation enforces; for the rest it detects and gives a recovery path. No package manager can promise an untouched system through power loss, filesystem errors or an irreversible hook.

Status words: **kept** (code + a test), **partly** (kept in the main path, a gap named), **gap** (not yet), **n/a yet** (the feature does not exist).

## The ten invariants

| # | Invariant | Status | Where / test |
|---|-----------|--------|--------------|
| 1 | A failed preflight does not modify installed package state | kept | `commands/preflight.rs` only reads; pre-flight e2e (`preflight.sh`) |
| 2 | A failed source rebuild after a successful upgrade leaves the repository binary installed and the preference pending | kept | `upgrade.rs::rebuild_policy`; `sourceinstall.sh` ("a rebuild that fails leaves the binary, keeps the policy") |
| 3 | A source preference never silently becomes a pin or a repository policy | kept | policy is its own file, `drop` and `install --binary` are the only ways out and are explicit; `sourceinstall.sh` |
| 4 | A system upgrade is resolved and committed as one pacman transaction (`-Syu`) | kept | `upgrade_official`; the source rebuild is a second, separate step by design |
| 5 | No signature, integrity, dependency or conflict check is silently bypassed (`--yes` included) | partly | pacman verifies signatures; `--yes` answers pacman's questions with their defaults and never skips emrac's gates (news, audit blocks, preflight). Gap: `--yes` with a HIGH audit still needs `--accept-risks`, which is tested only for AUR |
| 6 | Intended policy and actual installed origin are different facts | partly | `source_built::state_of` separates intent from the installed version; origin is inferred from the recorded version only. Gap: the installed package's `Packager`/build date is not compared |
| 7 | After an interrupted operation emrac inspects the real state before retrying or claiming success | kept for transactions | journal (`docs/design/journal.md`), `recover_found`. Gap: a rebuild interrupted mid-build leaves no `building` record (see S-2) |
| 8 | A failed transaction is never said to have left the system untouched unless verified | kept | the recovery report reads the database and ledger |
| 9 | A pending rebuild never blocks unrelated upgrades or causes a downgrade | kept | pending is a flag in `source-built.json`, not a pin and not an ignore |
| 10 | Every guarantee has a failure-condition test | partly | this register's last column; gaps below |

11. **Target state.** Every planned operation is resolved against one coherent target system state; emrac does not knowingly commit a transaction that leaves an unsupported mixture of versions. Binary and source-built packages follow the same planner. Status: partly (fresh syncs, partial-upgrade guard, plan id re-check; source rebuilds happen after the commit, not against the target state: `docs/plan/r3/source-system.md`).

## Source-build lifecycle (rules 16-34)

Kept: intent persisted across upgrades and emrac updates; failure keeps binary, intent and pending; `drop` is explicit; a package whose installed version differs from the one built is reported **unknown build intent**; the policy file is written atomically (temp file, fsync, rename); a rebuild is idempotent (a clean checkout every time; `record_to` replaces the entry).

Gaps:
- **S-1 States.** Only `built here`, `pending` and `unknown` exist. Missing: `building`, `failed` (with the reason and the log path), `blocked`. A failure is a pending flag plus a message in the terminal; the reason is not recorded (rule 128).
- **S-2 Operation record.** A rebuild is a history entry, but a crash mid-build leaves the policy unchanged without saying a build was running (rules 79, 81).
- **S-3 Recipe change.** The packaging revision is recorded but not compared: a changed recipe at the same version does not mark the build stale (rules 27, 28, 65).
- **S-4 Dependency order.** Several policy packages are rebuilt in plan order, not in dependency order; a policy package depending on another is not detected (rules 38-40).
- **S-5 Verified install.** "Built here" is recorded after `pacman -U` returns success; it is not re-read from the database (rule 20).
- **S-6 Schema.** `source-built.json` has no version field; the new fields are optional, so old files still read, but there is no migration path (rule 121).
- **S-7 Locking.** Read-modify-write of the policy has no lock; two emrac processes can lose an update. Transactions are already serialised by the journal state (rules 123, 124).
- **S-8 Locally modified packages.** Nothing marks a package built here as not the repository's file in `pacman -Qi` (it shows `Unknown Packager`); `from-source list` should show origin from the database (rule 33).

## Build isolation (rules 46-58)

Kept: builds run unprivileged in bubblewrap with the network off unless allowed, limits from `[build]`, the audit of the recipe before the build and of the built package before the install, downloads checked against the recipe's checksums by `makepkg`.

Gaps: the sandbox is bubblewrap over the host's installed packages, not a clean chroot from `devtools` (rules 47, 55: the build sees the host's library versions, which for a rebuild after `-Syu` is the intended target, but is not a clean-room); credentials/agents are not stripped beyond the sandbox's own mounts (rule 49: to be audited); the artifact's hash and the source checksums are not stored (rule 63). Scheduled: Build Profiles (u28) and the hardening slice (u29).

## Transactions and consistency (rules 1-15, 91-100)

Kept: one pacman transaction; pacman's own locking; no concurrent emrac transaction (journal `Running` refuses); the plan id is verified again immediately before the commit (`verify_before_commit`); databases are synced fresh for the plan (u22); `--expect-plan`; removals and replacements are simulated by libalpm and shown; commit failure and hook failure are reported by pacman's own words, and the recovery report says what landed.

Gaps: a package pacman fails to download aborts the transaction (kept) but the message is not classified as network/mirror/signature (rule 98); an offline plan from an old list is labelled stale, not refused for commit (rule 14: commit through `upgrade` needs the network anyway).

## Failure, recovery, state (rules 78-90, 121-130)

Kept: the journal, the ledger, `history reconcile`, `rollback`, atomic writes of emrac's JSON files, optional features (scores, stats) failing without stopping the package manager.

Gaps: the schema version of the JSON state files (S-6); a lock for policy files (S-7); "installed state and metadata disagree" is surfaced for the source policy (`unknown build intent`) but is not a general reconcile for all metadata (rule 90).

## Consent and CLI (rules 111-120)

Kept: the plan before any change; planned and done are different words; policy changes only by explicit commands; `--yes` does not pass the news gate, the audit's Block, or preflight refusals; noninteractive mode fails where a decision has no safe default.

Gaps: a pending rebuild is shown by `upgrade` when it happens and by `from-source list`, but not by `emrac doctor` or at the next `upgrade` plan (rule 119): to add.

## Tests required (rules 131-144)

Container checks exist for: failed rebuild keeping the binary (`sourceinstall.sh`), the policy surviving an upgrade, recovery after an injected pacman failure (`recovery.sh`), preflight, concurrent journal state. To add: crash during a rebuild (S-2), a changed recipe (S-3), two emrac processes on the policy (S-7), a corrupted/truncated policy file, an unreadable `source-built.json` (reads as empty today: should be reported as unknown, not as "no policy"), non-TTY runs of the rebuild step.

## Priority

- **P0** (before trusting it with real upgrades): S-1 `failed` with a reason, the unreadable-policy-file case (treated as unknown intent, never as "none"), S-5, the doctor/plan line for pending rebuilds, S-7.
- **P1**: S-2, S-3, S-4, S-6, S-8, artifact hashes and provenance, clean chroot.
- **P2**: snapshot integration for rollback of a source step, ABI-impact analysis, provenance reports.

Slice: these go into u29 (safety hardening). The unreadable-policy-file case is the one that most contradicts rule 32 today and is the first to fix.

## Audit of the code against the register (2026-10-19)

Read from the code, not assumed. Invariants 1, 2, 4, 8 and 9 hold; the others have these breaches.

- **A-1 (breaks 3, 32).** `source_built::read_from` returns an empty list for a file it cannot parse. `apply_source_policy` then plans no rebuild, so the next upgrade installs the binary without a word; and `record_to` after that writes a file with only the new entry, losing every other policy. Corruption must read as "unknown intent" and stop writes.
- **A-2 (breaks 12, 108, 79).** `upgrade::rebuild_policy` calls `history::begin` and, if it fails (another emrac running, a recovery that failed), builds and installs anyway: `if started.is_ok()` guards only the history record. It must stop for that package and mark it pending.
- **A-3 (breaks 120, 117).** `rebuild_policy` returns `Ok` when a rebuild failed, so `emrac upgrade` exits 0 although part of what was asked did not happen. It should exit non-zero (a distinct code for "upgraded, rebuild pending").
- **A-4 (rule 5, 116, 59).** `--yes` passes `--noconfirm`. pacman's default for "import this PGP key?" is yes, so a non-interactive run can import a key. Conflicts default to no and no `--force`, `--overwrite`, `--nodeps` or `SigLevel` override exists in the code (checked), but key import under `--yes` needs a decision: refuse, or require `--accept-keys`.
- **A-5 (rule 119).** A package pending since an earlier failed rebuild is not in the next upgrade plan unless the repository moves again, and `doctor` does not list it.
- **A-6 (rule 11).** The plan is checked again before commit only if more than 30 s passed since it was shown (`RECHECK_AFTER`). That is a deliberate cost trade-off; the strict reading is "always, immediately before".

Everything else in the sections above stands as written. Fix order: A-1, A-2, A-3, A-4, A-5, then the P0 list.

### Fixed after the audit

- **A-1 fixed.** `source_built::read_from` returns an error for a file it cannot read or parse; upgrade, `from-source` and every write refuse and leave the file untouched; `doctor` calls it a PROBLEM. Tests: `a_damaged_record_is_an_error_and_is_never_written_over`, three container checks.
- **A-2 fixed in code**: `rebuild_policy` builds nothing when `history::begin` fails; the package is marked pending. No automated test yet (needs an injected lock; add with the S-2 fault-injection set).
- **A-3 fixed.** `emrac upgrade` exits non-zero (`SourceRebuildPending`) after reporting the upgrade, when a rebuild failed. `--skip-source-builds` is a request and exits 0. Container check.
- **A-5 fixed.** Every upgrade plan (also an empty one) and `doctor` list pending rebuilds. Container checks.
- **A-4 open:** `--yes` and PGP key import needs a decision (see the conversation); **A-6** stays a deliberate trade-off.
- **S-8 / invariant 6 fixed.** Origin is checked against the package database (build date, packager) and reported as source verified, repository file detected, origin unverified, pending or mismatch; the version alone claims nothing. Build date and packager are evidence, not proof; the artifact checksum comes with the provenance record (S2).
- **A-4 reassessed and closed as far as emrac can.** Under `--yes` pacman imports a key it fetched (its default answer is yes), but an imported key is not a trusted one: with `SigLevel = Required TrustedOnly` (Arch's default) a package signed by a key nothing vouches for still fails with "unknown trust". The real exposure is a configuration that weakens that (`TrustAll`, `Optional`, `Never`). The pre-flight check `signature-policy` reads `SigLevel` for `options` and every repository (`pacman-conf`): Ok when none is weakened; a warning for an interactive run; a **problem that stops an unattended (`--yes`) run** when one is. `--yes` never trusts a key on its own. Not covered: a log of the fingerprints pacman imported, and pacman asking nothing about a key under `--noconfirm`; both need the pty runner and are listed for u29. The earlier statement that `--yes` "can import an unknown key" was right; that it bypasses verification was not. Tests: two unit tests; no container check (the tester user cannot edit `pacman.conf`).
- **Deleted record fixed.** The record has a seal beside it (`source-built.seal`: the names it holds). A missing record whose seal lists policies is an error that names them, never "no policy"; upgrades and writes refuse, `doctor` reports a problem. Ending the last policy removes the seal. Hand edits of a readable record are allowed. Tests: one unit test, three container checks.
- **Checked in the container** (`sourceinstall.sh`, 40 checks): a plan id changes with the policy and `--expect-plan` refuses the old one; a direct `pacman -Syu` leaves the policy reported as not honoured; a direct `pacman -R` leaves no claim of an installed source build; `install.prefer = recommend` never overrides `--source` or `--binary`.
- **Still open:** kills and power loss at three points (after the binary upgrade, mid-build, after the build before the install), a failing post-transaction hook, a full disk, multi-package runs with dependency failures. They need injection points; adding an environment variable that kills emrac inside a safety tool is a back door, so the plan is a test-only build feature (`--cfg emrac_fault`) rather than a runtime switch.
- **Fault injection added.** `emrac_core::fault::point(name)` exists only when built with `RUSTFLAGS="--cfg emrac_fault"` (`dev/e2e/run.sh sourceinstall` builds that variant into `target/fault`); a normal build has an empty inlined function and no switch. With it, `EMRAC_FAULT=<point>` aborts the process at `after-binary-upgrade`, `before-build` or `after-build`. Container checks (48 in `sourceinstall.sh`): cut off after the binary upgrade (TX-01: the upgrade is in the history as done, the binary is installed, the policy is reported as not honoured, the next rebuild completes), cut off after the build before the install (TX-03: the installed package is untouched, the built file is kept, the next run recovers the journal into the history and ends verified), and a real `kill -9` in the middle of a build (TX-02: same). TX-04 (journal against the real database) is covered by the last two.
- **Defect found by writing them.** `from-source rebuild` ran without the transaction lock, the journal or a history entry; it now begins and records a transaction like `install` and `upgrade`.
- **Still open:** TX-05 (a failing post-transaction hook), TX-06 (a full disk), PL-05 (several packages with dependency failures).
- **TX-05 done.** pacman exits 0 when a hook fails after the commit and says only `error: command failed to execute correctly`. emrac now listens (`hook_watch.rs`: the pty path sees the hook's name from the line before; the plain path listens to pacman's error stream and says "a hook"), records the transaction as committed, and after it prints which hook failed, that the packages are installed and the hook's work was not done, and **exits non-zero**. Tests: three unit tests, three container checks (a fixture package ships a hook that runs `false`). The pty path is covered by the unit tests only.
- **PL-05 partly.** An unknown name in the list stops the plan with nothing built or installed; two packages built from source in one request are both installed, verified and listed. Not tested: the second of two failing after the first was installed (the result should name both outcomes; the first stays installed and verified).
- **Found on the way.** An official package whose packaging repository is missing on Arch's GitLab (`tree`, `hello`) fails with git's "could not read Username": it should say the packaging source does not exist for it. To do.
- **Still open:** TX-06 (a full disk).
- **Build-dependency audit done (item 4).** The sandbox build's first step is `makepkg -s --verifysource --needed` on the host, which runs `sudo pacman -S --asdeps --needed` for what is missing at the version of the databases as last synced (no `-y`). With upgrades waiting that can drag an installed library forward alone: a partial upgrade the plan never showed. Now, before the build, emrac reads the `.SRCINFO` (never runs the PKGBUILD), works out with pacman what would be installed and what installed package would be upgraded, **says** the first, and **stops** on the second unless `safety.partial_upgrade` is `warn`/`off` or `--allow-partial` was given (`install`); a missing `.SRCINFO` is silently skipped. Not covered: the versions are the databases' of the moment, not recorded with the build (S2), and dependencies from the AUR. Container checks in `preflight.sh` (28).
- **PL-05 completed.** The second of two packages failing after the first landed: the result says "installed X; not installed Y", exits non-zero, nothing is undone. A missing packaging repository is said so (`explain_fetch_failure`, 1 unit test).
- **Pending is not one thing (rule 23a done).** Every installed policy package is judged by the same scan that finds stale AUR builds (`stale_builds::judge`: missing libraries, interpreter folders, a dependency's ABI bump logged after the build): **broken now**, **compatibility risk**, **risk unknown** (the files or pacman's log could not be read: a clean result without evidence is not "low"), or **low risk**. `from-source list` shows it after the state, `doctor` has a "Source builds against the system" check (problem / warning / note by the worst), and a failed rebuild after an upgrade says whether what is installed can still work. It is an estimate, not a proof: nothing blocks an unrelated upgrade because of it. Tests: one unit test (the four outcomes); one container check (a verified build with nothing changed is low risk and silent). Not tested in the container: broken and compatibility risk (they need a library removed or a logged ABI bump, which the unprivileged test user cannot fake).
- **`emrac bisect` has a hard boundary (u24).** It is the one command that installs older versions on purpose, so it is held to the strictest rule: protected packages (kernel, core runtime, init, package manager, boot and storage, essential utilities; policy in `protected.rs`) are never changed on a live host, there is no flag that lifts it, every step re-derives from pacman's own plan and libalpm's simulation what would be changed or removed, the end state is compared with an exact manifest taken at the start (a difference stops everything, keeps the snapshot and fails the command), and a window whose states cannot be visited ends with a range and "not reproduced is not ruled out", never a guess. Tests: 4 unit tests for the policy, 4 for reachability and the search, 19 container checks. Not covered by a test: the per-step guard firing (the reachability filter keeps steps away from it; it is the second line), and indirect removals by conflict in a bisect step. Planned: the isolated mode and the remediation workflow.
- **Bisect's second line of defence is tested.** A test command that changes a protected package itself makes the next step want to change it back: the step is refused before it changes anything, the search stops, the **ordinary** packages are still put back (the way back holds protected packages where they are), and the remaining difference is printed with the recovery command and makes the command fail. Found by writing it: the return used to be refused whole, leaving more drift than the protected package alone. 4 more container checks (`bisect.sh` 23). Still untested: indirect removals by conflict or replacement during a step (a contrived fixture: the history cannot contain a conflicting pair).
- **What was reviewed is what is built (campaign test 3).** The recipe (the tracked files of the checkout; every file but build output for a plain directory) is hashed when it is reviewed or audited and checked immediately before `makepkg`; a difference stops the build with the files named (`RecipeChanged`) and asks to run it again. Found by testing: `makepkg --packagelist` also sources the PKGBUILD on the host, so the baseline is taken before it, and the comparison is repeated after each host step; a PKGBUILD that rewrites itself while being sourced is caught before the sandboxed build. Tests: 5 unit tests, 5 container checks (an edit, an untracked file that changes nothing, a deletion, self-modification, an unchanged recipe). Not covered: `--no-sandbox` builds after they start, and downloaded source archives (their checksums are the PKGBUILD's, checked by makepkg).
- **Concurrency and crash sweep (campaign tests 1 and 2).** The policy record has a lock (`flock` on `source-built.lock`, bounded wait, refused rather than changed without it; S-7 closed): a unit test with 40 threads loses nothing with it and fails without it, and six emrac processes in the container add and end policies at the same moment without loss. A second emrac during a transaction is refused ("another emrac is changing packages") and the first finishes normally; emrac refuses while pacman runs a transaction. The same rebuild is cut off at nine named boundaries and after each the record, the installed package, the journal, the history and the ledger agree and the next run completes it (9 checks). **Defect found by the sweep:** a cut between writing the history record and clearing the journal made the next run record the same transaction a second time as "interrupted" (once committed, once failed). The journal now keeps the number of the newest history record and the plan digest, and recovery recognises a run that was already recorded and records nothing more. Not covered: `install`/`upgrade`/`remove`/`restore` sweeps, a cut during `pacman -U` itself, pacman started between emrac's plan and its commit.
- **Pacman between emrac's plan and its commit (closed; A-6).** The plan is made again just before the commit not only after 30 s but whenever pacman's databases are not as they were when the plan was made: a cheap fingerprint of the installed packages (the entries under `local`), the size and time of each synced database and the lock. If pacman installs the very package in between, the run is refused ("the plan changed while you were deciding … Nothing was changed"); an unrelated install or a database sync makes emrac check again, find the same plan and go on. To make "pacman installed it in between" visible to the plan, an install plan now records the version already installed (`previous_version`), as the source-build plan already did. Tested in the container (PC-01..03) and with unit tests.
- **Crash sweep for install and upgrade, and a power cut.** `install` is cut off at five boundaries and `upgrade` at six; after each, the installed packages match what happened (installed iff pacman had finished), the next command works, no interrupted transaction is left, `history verify` and `pacman -Dk` pass, and the history gained exactly two records (11 checks). A power cut in the middle of `pacman -U` (emrac and pacman killed together during a package's pre-install script) leaves no half-installed package and a consistent database; the next emrac command records the cut-off transaction as failed and goes on, and the install can be done again (3 checks; pacman's stale lock is removed by hand). Not swept: `remove`, `restore`, `downgrade`.
