# Changelog

All notable changes to Emrac are recorded here, newest first. Each entry lists the date, the commit it corresponds to, and what changed and why.

Emrac uses **Slices** instead of semver, in three tiers that cycle per release:

- **Slice i\<N\>** — incubation for release `r<N>`: work-in-progress leading up to that release (code, docs, planning — not code-only).
- **Slice r\<N\>** — major release versions (`r1`, `r2`, ...).
- **Slice u\<N\>** — update cycle versions within a release; resets to `u1` at the start of each new `r<N>`.

The cycle repeats every release: `i1 → r1 → u1 → u2 → ... → i2 → r2 → u1 → u2 → ... → i3 → r3 → ...`. `i1 → r1` ships once the core CLI loop MVP (`search`/`info`/`install`/`remove`/`upgrade` against official repos + AUR, per `SPEC.md` Part X) is complete and verified; later `i<N> → r<N>` transitions are a per-release judgment call.

(See `SPEC.md` Part X for the milestone philosophy this follows.)

## Slice u23 — 2026-10-14 — pacman's own prompts, and silence is not consent

Asked whether emrac could pass pacman's prompts through. It could not: every mutating command ran pacman with `--noconfirm`, so a package conflict (`pipewire-jack` vs `jack2`: "Remove jack2? [y/N]"), a provider choice or a replacement took pacman's default — and the default for a conflict is *no*, so a conflicting install could only fail even when you wanted it. **Without `--yes`, pacman now runs with the terminal attached and no `--noconfirm`, so it asks** (install, remove, purge, upgrade, every `pacman -U` path, and the dependency step of `makepkg -s`); `--yes` keeps meaning fully non-interactive. The sandboxed build steps stay `--noconfirm` (no prompt can occur there). The cost is a second "Proceed with installation?" from pacman after emrac's own.

**A real safety bug found on the way:** `confirm()` is documented to return false when it cannot read an answer, but end of input is not a read error — it came back as an empty line, which `[Y/n]` treats as yes. With a closed stdin and no `--yes`, `emrac install foo` **proceeded without anyone answering**. No answer at all (end of input, a read failure) is now always a no, whatever the default; an empty line still takes it. Also: prompts read one byte at a time up to the newline, because `std::io::stdin()` takes a whole buffered block and so, with piped input, emrac's first prompt swallowed every line and the pacman started afterwards saw end of input — scripted answers (`printf 'y
y
y
' | emrac install …`) now reach pacman. Design in `docs/plan/u23-pacman-prompts.md`.

Verified with 3 argument tests (`--noconfirm` present exactly when non-interactive, for install, upgrade and remove; the rest of each command identical; the default unchanged) and 4 tests of the decision rule incl. "end of input is never consent" — 201 core, 18 CLI integration, 8 CLI unit. Through a **real pseudo-terminal** in the container: answering yes to emrac, to pacman's `Remove jack2?` and to its final confirm replaces `jack2` with `pipewire-jack` (impossible before); answering no to the removal aborts cleanly with nothing changed; `--yes` behaves as before. With a closed stdin and no `--yes` nothing is installed (it used to install); a bare Enter still means yes; `n` declines; scripted answers reach pacman.

Not done: emrac's plan for an install doesn't list packages that conflict resolution will remove (`install pipewire-jack` planned "1 package" without saying `jack2` goes); pacman's prompt now shows it at execution, but the preview should too — the same class of fault as u22, and next.

## Slice u22 — 2026-10-14 — upgrade previews that match reality

**A bug in what I shipped, reported by the owner:** `emrac doctor` said "Pending upgrades: up to date" on a machine whose package list was 11 days old. Chasing it found the same flaw in `emrac upgrade` itself, which was worse: its plan was built from the sync databases *as last refreshed*, but the real step runs `pacman -Syu`, which refreshes first. On this host the plan listed **0** of the **347** official updates `checkupdates` finds (only 23 AUR packages showed); with an empty stale plan it printed "nothing to upgrade — you're already up to date" and returned before any refresh; and if even one official package had been in the stale view, the confirmed upgrade would have applied all the unseen ones. A preview that doesn't match what happens breaks the central promise of a preview-and-confirm tool.

Fixed in two steps. `doctor` first (`b7620bb`): a pending-upgrade result from a list more than a day old is never "ok" and never says "up to date" — it says how old the list is and that it can't tell. Then the real fix: the upgrade plan is now built from a **freshly synced throwaway database**, the way pacman-contrib's `checkupdates` does it — a private 0700 directory under `$TMPDIR` (created and verified owned-by-us, not a symlink, not group/world accessible, since it sits at a predictable name in a shared place) whose `local` is a symlink to the real local database, filled by `fakeroot -- pacman -Sy --dbpath <dir>`. The real database is never touched and no root is needed; the directory persists, so later runs download only what changed. Names come from `pacman -Su --print --dbpath <dir>`, versions and sizes from a libalpm handle on it, pins are honoured. When it can't refresh (`--offline`, no network, no `fakeroot`) the plan falls back to the stale list **and says so** — how old it is, why it couldn't be refreshed, that the real upgrade may include more — and an empty stale plan is never reported as up to date. New **`emrac doctor --online`** gets its count from the same fresh view (it needs the network, so it is opt-in; the default stays offline and honest about the list's age). Named-package installs and upgrades are unchanged: they resolve and execute against the same current local databases, so preview and execution already agree. Design in `docs/plan/u22-fresh-upgrade-view.md`.

Verified with 6 new `doctor` tests (fresh vs stale for 0/1/2/10/400 days and no date, the "probably more" wording, trusting `--online` regardless of the local list's age, a failed online check saying so, and a whole-report assertion that nothing says "up to date" from an old list), 5 tests of the private-directory safety check (created 0700 and accepted again; open permissions, a symlink, a file in the way and another owner all refused), 2 of the freshness decision and 3 of the stale-plan note — 198 core, 18 CLI, 4 CLI unit in total. **Measured**: on this host (list 11 days old) the new plan lists 365 official packages against `checkupdates`' 347; the 18 extra are all *not installed* — new dependencies (`ghostscript`, `graphviz`, `netpbm`, …) the upgrade pulls in, which `pacman -Qu` can't show and `pacman -Su` installs — and nothing `checkupdates` finds is missing; the real database's modification time was unchanged by the preview; `doctor --online` agrees with the plan (365). In a clean container with a 4-day-old list: the old method planned 0, `checkupdates` finds 3, the new plan 3. `--offline` and a PATH without `fakeroot` both fall back with an explicit explanation instead of "up to date".

Not changed: whether the *local* list is stale is still `doctor`'s sync-database warning; installing a named package from a stale list is the usual partial-upgrade hazard that warning exists for.

## Slice u21 — 2026-10-14 — doctor

New `emrac doctor` (from `ideas.md` and SPEC's Health Center): read-only health checks of the whole system, no root and no network, in under a second on a 1,600-package machine. Each check is **ok**, **note**, **warning** or **problem**, with specifics and a fix hint, problems first. Checks: unmet dependencies of installed packages (what `pacman -Dk` finds — the visible signature of a partial upgrade or a forced removal); a stale `db.lck` (a problem only if no pacman is running); sync-database age (a warning after 7 days — installing from a stale database is how partial upgrades start); pending upgrades; `.pacnew`/`.pacsave` files left under `/etc`; failed systemd units (system and user); a running kernel whose modules directory is gone (the kernel was upgraded under you — reboot); free space on `/` and on pacman's cache filesystem (warning under 10 % or 5 GiB, problem under 1 GiB); pacman's cache and emrac's own caches; orphans (u12); expired pins (u13); failed transactions in the last 7 days (u3); `config.toml` parses and isn't world-writable; the tools emrac shells out to, each with its own package in the fix; and whether the build sandbox really works here and whether memory/process limits are available (u19/u20). Exit status is `1` when there is any *problem*; warnings and notes don't fail a script. `--json` returns the checks; **`--report`** prints a markdown block for a bug report — emrac and pacman versions, kernel, package counts, every check — with your home directory, user name and host name scrubbed, so it can be pasted publicly. Every status decision is a pure function of a plain `DoctorInputs` struct, so the logic is unit-tested without touching the system. Design in `docs/plan/u21-doctor.md`.

Found while testing in the podman container: "the running kernel's modules are gone" fired falsely there (a container shares the host's kernel and has no modules of its own), so the check now applies only where `/usr/lib/modules` holds a kernel; the missing-tools hint named the same packages whatever was missing, so each tool carries its own; and pacman's version line came out behind its ASCII-art banner.

Verified with 16 unit tests of the status logic (thresholds, ordering, capping, scrubbing, parsers) and 2 CLI integration tests (the JSON shape, problems-first ordering and the exit status; the report is markdown and contains no user, host or home path) — 186 core, 18 CLI in total. **Against ground truth on this host**: the 5 `.pacnew` files match `find`, the one failed unit (`vboxdrv.service`) matches `systemctl --failed`, 15 orphans match `pacman -Qdtq`, the database age matches the file dates, and "no unmet dependencies" matches `pacman -Dk`. **In the container**: a fresh image reports only real findings; removing `fuse-common` from under `fuse3` with `pacman -Rdd` is reported as `fuse3 needs fuse-common`, exits 1, and exits 0 again once reinstalled; a stale `db.lck` is a problem with the fix `sudo rm /var/lib/pacman/db.lck`.

Not checked: anything needing the network or root (AUR packages removed upstream, keyring expiry) and a full library scan (slow and noisy) — `emrac verify` covers file integrity per package.

## Slice u20 — 2026-10-14 — resource limits for sandboxed builds

The sandbox hides things from a build; now it also bounds what a runaway or hostile build can consume. Four limits, all applying to the two sandboxed `makepkg` steps (the host step that installs dependencies and fetches sources needs `sudo` and the network and stays outside; `--no-sandbox` builds have no limits, which is what the flag means): **memory** (a cgroup `MemoryMax` of 75 % of total RAM, swap disallowed), **processes** (`TasksMax` 4096, which stops fork bombs), **size** of the build's `/tmp` and `$HOME` tmpfs (`bwrap --size`, 8 GiB each) and **time** (120 minutes, then emrac kills the sandbox and everything inside it). Memory and process limits go through `systemd-run --user --scope`, because bubblewrap has no cgroup support. Configurable with `emrac config set build.timeout_minutes | build.memory_percent | build.max_tasks | build.tmpfs_gib`; `0` turns a limit off. Unlike `--no-sandbox` these may live in the config, since they only restrict a build.

When a limit stops a build the error says which one and which knob to turn: "It hit its memory limit (75% of RAM) and was killed; raise `build.memory_percent`", "It hit its process limit (4096 tasks); raise `build.max_tasks`", "timed out after 120 minutes. Raise `build.timeout_minutes`". If the user manager can't give a scope (no systemd user session, cgroup v1, a container) emrac says so once and carries on with the time and size limits, which need nothing — it never pretends to enforce what it can't. Design in `docs/plan/u20-limits.md`.

Found while testing: systemd's default `OOMPolicy=stop` answers the first OOM kill by terminating the whole scope, leaving nothing to report, so the scope uses `OOMPolicy=continue`. And **diagnosing the kill by polling the cgroup from outside cannot work** — the cgroup disappears within milliseconds of its last process exiting, right after the kill — I measured it naming the cause in only 4 of 12 runs, and a first version even latched onto the terminal's own scope. The scope now runs a small wrapper shell that stays inside the cgroup until it has read `memory.events` and `pids.events` itself and hands them over in a file; that is deterministic.

Verified with 8 new unit tests (the `systemd-run` property builder incl. `OOMPolicy` and zero-means-off, `--size` placement, config conversion, the timeout runner killing a real `sleep` on time, the counter parsers incl. the two different `max` lines, the wrapper's exit-status hand-back) and 4 config tests for the new keys, plus 2 CLI integration tests against the real binary (170 core, 16 CLI in total): a build that eats memory without end under a 1 % cap is stopped and named, a fork loop under a 32-task cap is stopped and named, and without a systemd session the warning appears and the build still succeeds (no warning when both limits are off). Measured on real builds: memory kill explained **12 of 12**, fork bomb **6 of 6** with no leftover processes, a 1-minute timeout fired at 62 s with no leftover processes or stray files, and a build allocating 1.5 GB runs normally with the memory limit off. In the podman container (no systemd session) the sandboxed install warns once and installs.

Not done: Landlock as a second layer, a throwaway root hiding the host's installed packages from the build, CPU caps (deliberately: a build should be fast), ccache.

## Slice u19 — 2026-10-13 — sandboxed AUR builds

The build step of every AUR package now runs inside bubblewrap (the design in `docs/design/source-build.md`, with the owner's decisions: host `makedepends` visible read-only, `bwrap` an optional external dependency, **warn-and-ask** for network). `makepkg`'s own flags give the phases (read from `/usr/bin/makepkg` 7.1, then proved by hand): (1) on the host, `makepkg -s --verifysource` installs dependencies and downloads and verifies sources — the only part that needs `sudo` and the network; (2) in the sandbox, `--nobuild --nodeps --cleanbuild` extracts and runs `prepare()`/`pkgver()`; (3) in the sandbox, `--noextract --nodeps` runs `build()`/`check()`/`package()` and makes the archive. An already-built package skips all three.

The sandbox: `--unshare-all --die-with-parent --new-session`, a read-only root, fresh `/dev` and `/proc`, `tmpfs` over `/tmp`, `/home`, `$HOME` and `/run/user`, a writable bind of only the build directory plus any `SRCDEST`/`PKGDEST`/`BUILDDIR`/`LOGDEST` from the user's makepkg config, and a **cleared, whitelisted environment** (`GITHUB_TOKEN`, `SSH_AUTH_SOCK`, `AWS_*`, dbus addresses never reach the build). Same uid, so makepkg's refusal to run as root and `fakeroot` both work. **Network is off** for steps 2–3. If the audit expects network use in `prepare()`/`build()`/`check()`/`package()`, emrac warns and asks — default no, **not answered by `--yes`**; `--allow-network` answers yes; a build that fails with the network denied says so and names the flag. `bwrap` is probed by actually running it with the same mounts as a real run; if it isn't usable emrac **refuses** and says how to fix it, and `--no-sandbox` (a flag, deliberately never a config key) builds as before with a loud warning.

New **`emrac build <target>...`** (a SPEC command): builds AUR packages (same review and audit as `install`) or a local PKGBUILD directory (audited first: critical refuses, high asks) in the sandbox, prints the manifest and the package paths, installs nothing. `install`, `upgrade` and the AUR rebuild in `reinstall` use the sandbox by default and accept `--no-sandbox` and `--allow-network`. Design in `docs/plan/u19-sandbox.md`.

Found while testing: the availability probe lied. In a rootless container `bwrap` can create namespaces but cannot mount a fresh `/proc`; a probe without `--proc` reported "usable" and the build then failed halfway. The probe now uses the same mounts as a real run. A host `/proc` is deliberately **not** a fallback — a shared `/proc` would let the build read emrac's own `/proc/<pid>/environ`, defeating the cleared environment. For the test container, `--security-opt 'unmask=/proc/*'` is enough (no capabilities, not `--privileged`); `dev/container/run.sh` passes it and the Containerfile installs bubblewrap. Also: `$HOME` must exist inside the sandbox, so it is an empty tmpfs.

Verified with 6 unit tests of the pure `bwrap` argument builder and environment filter, and a CLI integration test that runs a **real sandboxed build** against a real listening socket (skipped where `bwrap`/`makepkg` can't run; 162 core, 14 CLI in total): sandboxed, the build reaches nothing (0 connections), sees no token or agent socket, a read-only `/etc`, an empty home, and its write to `$HOME` never reaches the host; with `--allow-network` it connects. By hand on the host with the unsandboxed run as control: sandboxed, `token=none`, `net=000 blocked`; `--no-sandbox`, the real token is visible and the build wrote a file into the real home. The warn-and-ask path: declining builds offline and fails with the hint, `y` works, the flag skips the question, `--yes` alone does not answer it. **In the podman container with real `makepkg` and `pacman -U`**: no bubblewrap → refused with the install hint; `--no-sandbox` → warning, builds; sandboxed install of a benign package; a `package()` that reads `~/.ssh/id_test` (which exists outside) and tries to write `~/pwned` and `/usr/bin/evil` finds no `~/.ssh` and leaves nothing behind; the upgrade path is sandboxed; the audit still refuses critical code before any build.

Not done: Landlock as a second layer, cgroup limits (memory/CPU/time), a throwaway root so the host's installed packages are hidden from the build, ccache. The sandbox does not protect against what the *installed* package does — that is what the audit and the manifest are for.

## Slice u18 — 2026-10-13 — closing the gaps left by u15–u17

Each item here was named as "not covered" earlier.

**Scripts shipped inside a built package are now read.** One `bsdtar` extraction of exactly the wanted small members (hooks, units, sysusers, sudoers, `profile.d`, and up to 300 executable or script-looking files of at most 128 KiB, outside documentation directories) goes into a private 0700 temporary directory that is removed afterwards — nothing is executed, ownership and special bits are not restored. Scripts keep only dangerous-pattern findings, never above *high* (they are programs the user chose to install; even legitimate container templates write `authorized_keys`), credential reads and `LD_PRELOAD` are warnings, and the style-level notes that autotools-generated scripts produce by the thousand are dropped. Compiled executables and nested archives can't be judged by static rules, so the summary now **counts** them ("executables and libraries that are not scripts: N", "nested archives or bundles: N") instead of staying silent. The single extraction also replaced one `bsdtar` run per file for the config files already read.

**Credentials read in one file and sent from another are correlated.** The audit collects reads and uploads across the PKGBUILD, scriptlet and every extra file and rates an upload *critical* when any other file reads credentials.

**Opt-in inspection of official packages: `--inspect`** (or `review.inspect_official = true`) on `install` and `upgrade` downloads first (`pacman -Sw` / `-Syuw`, honouring pins), prints the manifests of packages that have something to note plus a one-line summary, and then installs. Deliberately lighter than for AUR builds — official packages are signature-verified and legitimately ship setuid helpers and hooks — so findings are *shown*, and only a *critical* one stops the install.

**Found and fixed along the way:** `VAR=value command args` at the top level was parsed as a plain assignment and the command never scanned (`LD_PRELOAD=./x.so make`, `FOO=1 rm -rf /`); `obfuscated-command` fired on `$'\033[1m'` colour codes and now needs a first word of at least three hex/octal escapes; and **the unexplained blank run from u17 was real** — one slow AUR RPC response (`the AUR didn't cooperate: … timeout: global`) failed a whole `install`. The AUR client now waits 10 s (was 5) and retries timeouts, connection errors and 5xx/429 twice with a short backoff; a 4xx or malformed answer still fails at once. Design in `docs/plan/u18-close-gaps.md`.

Verified with 5 new manifest unit tests, 3 audit tests (cross-file correlation, env-prefixed commands, escape-spelled commands) and 1 retry test, plus 1 CLI integration test that builds a package and also checks, with a private `TMPDIR`, that the extraction directory is gone (156 core, 13 CLI in total). **Calibration over all 932 packages in a pacman cache**: no critical finding; high findings are 17 legitimate setuid helpers and four packages whose shipped scripts really do the flagged things (`kitty`, `kitty-shell-integration`, `lxc`, `parallel`); ~80 ms per package. The PKGBUILD survey is unchanged by the new rules. **In the podman container with real pacman/makepkg:** `install --inspect` downloaded, reported "1 clean" and installed; `install fuse3 --inspect` showed the setuid `fusermount3` and installed anyway; `upgrade --inspect` listed perl's `profile.d` script and hook before upgrading; the **`reinstall` AUR rebuild branch**, never run before, ran makepkg once, showed the manifest and installed; and the setuid scenario that failed 1 run in 6 before the retry passed **20 of 20**.

Still not coverable, by static means: what a compiled binary does, a sufficiently obfuscated payload, behaviour that only appears at runtime. The sandbox slices are the mitigation.

## Slice u17 — 2026-10-13 — build/install split and package manifest

AUR builds no longer go through `makepkg -si`. emrac runs `makepkg -s --noconfirm --needed` (build dependencies still come in through makepkg's `sudo pacman` path, but the package is **not** installed), collects the exact package files from `makepkg --packagelist` (split packages included; makepkg's "already built" exit is accepted and the existing file used), **inspects the built package**, and only then installs it with `sudo pacman -U`. This closes the last limit named in u15/u16: the source audit can't see what `package()` produces. Inspection is by `bsdtar` (libarchive, already a pacman dependency), reading only — nothing is extracted or executed — and covers the file list with modes, `.PKGINFO`, the packaged `.INSTALL` scriptlet and the few small files whose content matters.

The manifest prints for every AUR build (to stderr): file count, installed size, and a plain summary — install scriptlet and its functions, systemd units, users and groups created, pacman hooks, replaces/conflicts, config files kept. Findings use the audit's severities and policy: **critical** (`/etc/ld.so.preload`, or code in a hook/unit/scriptlet that the script rules rate critical) → refused, no override, the built file is kept and its path given; **high** (setuid files, sudoers drop-ins, cron entries, files in `/home` or `/root`, dangerous code in a hook/unit/profile script/scriptlet) → the default-no prompt that `--yes` does not answer and `--accept-risks` does; otherwise it installs without a further question. Warnings: setgid, enabled-by-default units, `profile.d` scripts, plain pacman hooks (what a hook *runs* is scanned as code and escalates it), files outside the usual directories. The same path serves `install`, `upgrade` and the AUR rebuild in `reinstall` (which gained `--accept-risks`).

`emrac audit <file.pkg.tar.*>` inspects any package file the same way — before a `pacman -U` on something downloaded, or on a cached package. Design in `docs/plan/u17-manifest.md`.

Found while testing: the script rules were quote-aware, so a payload passed as a string (`sh -c 'echo k >> ~/.ssh/authorized_keys'`, `bash -c "curl … | sh"`, `eval '…'`) was never read — in PKGBUILDs and shipped scripts as much as in hooks. The scanner now recurses into `sh -c` and `eval` strings.

Verified with 14 new unit tests against real `bsdtar -tv` output of a makepkg-built fixture (listing parser incl. spaces, symlinks and setuid/setgid/sticky bits; every rule; hook content escalation; verdicts) and 2 CLI integration tests that build package archives (150 core, 12 CLI in total). **Calibration over all 932 official packages in a pacman cache**: no critical finding; the only high findings are 17 legitimate setuid helpers (`fusermount`, `mount.cifs`, `chrome-sandbox`, …); 44 packages ship a hook, which is why a plain hook is only a warning. The PKGBUILD false-positive survey is unchanged by the new recursion. **End to end in the podman container with real `makepkg` and `pacman -U`**, using a local "upstream" under a real AUR name: a benign package builds, shows "nothing here needs your attention" and installs; a package with a setuid file stops (exit 1, `--yes` and a closed stdin both mean no), keeps the built file, and a re-run (makepkg's already-built path) installs it on `y` with mode 4755 on disk; `--accept-risks` installs without asking; a package shipping `/etc/ld.so.preload` is refused, nothing is installed and the file is kept; a hook running `curl | sh` is high and is declined.

Not covered: the manifest does not look inside binaries or archives shipped in the package (it can't tell what an ELF does); official-repo packages are not inspected during `install` (pacman has verified their signatures; `emrac audit <file>` works on them); the rebuild branch of `reinstall` shares the helper but wasn't separately exercised because a previously built file is normally reused.

## Slice u16 — 2026-10-13 — audit coverage

Follow-up to the limits stated in u15. **The rest of the repo is now read**: every file at the audited revision (the PKGBUILD's own git revision — `FETCH_HEAD` for a pending update — so it is what would be built) is classified. Helper scripts (by shebang or extension, plus other `.install`/`.hook` files) get the dangerous-pattern rules at full strength but not the PKGBUILD-only ones, since a shipped wrapper may legitimately use `sudo`; patches are judged by their **added** lines only, capped at warning and labelled "added by this patch"; a committed ELF binary is **high**; other binaries and archives are warnings; docs, licenses, keys, images, fonts and metadata are skipped; files over 1 MiB are noted as unscanned; at most 200 files are read. Directory targets are walked (not `.git`, `src`, `pkg`, built packages); a single-file target looks only at the files beside it.

**More obfuscation is caught**: a file downloaded and run later (`curl -o i.sh …; sh i.sh`, `wget -O i …; chmod +x i; ./i`) is high; unpacking straight into an interpreter (`gpg -d`/`zcat`/`tar -O`/`unzip -p … | sh`) is high; a command spelled with `$'\x..'` escapes is high; a command word built at runtime (`$a$b`, `$(…)`) and long encoded blobs are warnings; `curl … | sh` inside a quoted `os.system(…)`, `exec(b64decode(…))` and the multi-line Python socket + `dup2`/`pty.spawn` reverse shell are caught in non-shell scripts too. Command substitution in top-level assignments (`x=$(curl … | sh)`, which runs when the PKGBUILD is merely read) now reaches the command rules.

**Found by the survey and fixed**: `install=$pkgname.install` — the usual form — was never resolved, so most scriptlets had not been read at all; persistence is now judged by where a command *writes*, not by a path appearing on the line (`grep x /etc/passwd > /dev/null` is no longer a hit); shell startup files are **high** in install scriptlets/shipped scripts (critical in a PKGBUILD) because legitimate packages such as `nvm-git` append a `source` line there, while SSH keys, `ld.so.preload`, sudoers and account files stay critical everywhere (a refinement of the severity table, recorded in the design doc); the command-word reader now handles `case`/`for`, array assignments and `x=$(cmd …)`, cutting `dynamic-command` noise from 39 to 6 and sharpening the other rules. Design in `docs/plan/u16-audit-coverage.md`.

Verified with 14 new audit unit tests (36 in total) and a CLI integration test over a package directory (a clean PKGBUILD and scriptlet with the payload in a helper script, a patch, a binary and an ignored `src/`). **Survey over every file** of 38 current official PKGBUILD repos and 29 popular AUR repos: no high or critical finding on any official package; the only AUR hit is `nvm-git`, a true positive that now stops to ask. End to end against a poisoned upstream (real checkout, scratch `$HOME`, nothing built): a clean PKGBUILD whose helper script writes `authorized_keys` is refused under `--yes --skip-pkgbuild --accept-risks`; a patch adding `curl | sh` is a warning with no extra prompt; a committed ELF and a download-then-run script each stop at the default-no prompt.

Still open: findings are per file (a credential read in one file and an upload in another are not correlated); the manifest of what the *built package* installs needs the build and install steps split and is its own slice.

## Slice u15 — 2026-10-13 — audit

New `emrac audit <target>...` reads a PKGBUILD (and its `install=` scriptlet) for risky code **without running any of it**. A target is an AUR package name (emrac's git checkout is fetched but not advanced; what upstream has now is audited) or a path to a PKGBUILD or its directory — paths need no pacman. It prints findings (rule, severity, `file:line`, message, the line itself) or `--json`, and exits 1 if any target has high or critical findings so scripts can gate on it. The reader (`audit.rs`) understands assignments including multi-line arrays, `declare`/`export` forms and `name[i]=`, functions in all common shapes, quotes, comments, backslash continuations and heredocs (data, not code); a value computed by a command is reported as *dynamic* rather than guessed. Commands are split into pipeline stages and seen through wrappers (`sudo`, `env`, `nohup`, `timeout`, …), so `curl … | sudo bash` and `sudo rm -rf /` are caught.

Severity policy (design owner's decision, `docs/design/source-build.md` §6): **info** and **warning** are only shown; **high** (download piped into a shell, `sudo`, setuid outside the package, `systemctl enable`, reading `~/.ssh` or browser data, LD_PRELOAD, host-changing commands) makes `install`/`upgrade` stop at an `emrac asks:` prompt that defaults to *no* and that `--yes` does **not** answer (`--accept-risks` does); **critical** (writing `.bashrc`/`authorized_keys`/`ld.so.preload`/sudoers, reading credentials *and* sending data out, decode-and-execute, reverse shells, `rm -rf /`-class commands) is **refused by emrac with no override** — the user can still read and build by hand. The audit runs on exactly the PKGBUILD and scriptlet about to be built, on every `install`/`upgrade` of an AUR package, even with `--skip-pkgbuild`/`--skip-diff` and when the checkout is up to date; a refusal happens before the checkout is advanced. Findings go to stderr so structured stdout stays clean. Also flagged as warnings: `http://` sources, `SKIP` checksums on downloads, missing checksums, network use inside `build()`/`check()`/`package()` (the sandbox slice will block it), writes outside `$srcdir`/`$pkgdir`, `eval`, code that runs when the PKGBUILD is merely read. Design in `docs/plan/u15-audit.md`.

Verified with 23 audit unit tests and 2 CLI integration tests (125 core, 10 CLI in total): every rule both ways, wrappers, scriptlets, line numbers, verdicts, JSON, a no-PKGBUILD error. **False-positive survey** over 38 current official-repo PKGBUILDs and 29 popular AUR PKGBUILDs (linux, glibc, openssh, systemd, sudo, firefox, chromium, docker, yay, paru, google-chrome, spotify, …): the first run found real false positives — `empty.sshd` matching `.ssh`, backslash-continued option lines read as commands (`--with-rundir=/run/sudo` as `sudo`), `pacman -T` as a host change, multi-line arrays inside functions and `declare -A` tables read as commands — all fixed at the cause and pinned by regression tests; the final run has **no high or critical findings** on any of the 67. End to end with a poisoned "upstream" behind a real checkout (scratch `$HOME`, nothing built): a critical PKGBUILD is refused under `--yes --skip-pkgbuild --accept-risks` and the checkout stays put; a high one asks, `--yes` and a closed stdin both mean no, `y` continues to the normal review, `--accept-risks` skips only that prompt; a warnings-only one gets no extra prompt.

Limits, stated in the output: pattern rules can miss obfuscation they don't know and can flag legitimate code; extra files in an AUR repo (patches, helper scripts) are not scanned yet; the manifest of what the *built package* installs is u18.

## Slice u10 — 2026-10-11 — snapshot and restore

## Slice u9 — 2026-10-11 — verify

New `emrac verify <pkg>...` (alias `check`) checks that installed files still match what pacman recorded — `pacman -Qkk` with a clearer report and a pointer to `emrac reinstall` for repair. It reads the package's gzip `mtree` from the local db (parsed here with `flate2` and ~60 lines of mtree parsing: `/set`/`/unset` defaults, `\NNN` octal escapes, type/mode/size/sha256/link — libalpm's iterator doesn't expose the digests) and compares each entry with the filesystem under pacman's `RootDir`: missing, wrong type, size, SHA-256 contents, permission bits (incl. setuid/sticky), symlink target. Not checked, on purpose: mtime and owner uid/gid (an unprivileged user can't be expected to match; noisy). Edited `backup=()` config files are reported as "config edited", not as problems (same stance as pacman), though a missing or wrong-mode config file is still a problem. Files an unprivileged user can't read are counted ("couldn't be read — run as root for a complete check") and never treated as damage. The report is printed first; then any real problem makes the command exit 1 with a summary naming the packages and the `emrac reinstall ...` that repairs them, so scripts can use it. Names that aren't installed abort together. Read-only, no root, `--json`, not logged in the history. Design in `docs/plan/u9-verify.md`.

Found while testing in the stock Arch container image, whose `pacman.conf` `NoExtract`s docs, locales and man pages: the mtree describes the whole package, so those files were reported missing. Pacman's `-Qk` skips them, and so does `verify` now — by matching each entry against `pacman-conf NoExtract` (fnmatch-style globs where `*` crosses `/`, `!` re-includes, last match wins, directories matched with a trailing `/`) and by dropping entries absent from libalpm's installed file list.

Verified with 14 new unit tests (mtree parsing incl. defaults/overrides/unset/escapes/links/metadata files, each damage kind against a temp root, clean package, edited vs. missing vs. wrong-mode config, unreadable not a problem, plain and gzip mtree files, NoExtract glob semantics incl. `!` and directories, installed-file-list filtering). New `emrac purge <pkg>... [--cascade] [--recursive]`: `emrac remove` with `pacman -Rn`. ## Slice u7 — 2026-10-11 — reinstall

New `emrac reinstall <pkg>...` puts the **installed version** of each named package back (repair a damaged or deleted file, re-run install scripts). It deliberately never reinstalls the repositories' *newer* version: a plain `pacman -S pkg` would turn a reinstall into a partial upgrade, so each package picks a source in order — a package file for exactly the installed version already on disk (`pacman -U`), else the repositories if they still carry that version (`pacman -S`), else the Arch Linux Archive (downloaded after confirmation, then `-U`), and for an AUR package a rebuild (`makepkg -si`) of the existing, already-reviewed checkout, with no new PKGBUILD fetched. If a package can't be had at the installed version the whole command aborts before prompting, naming each package and why (including "the Archive wasn't checked (--offline)"); names that aren't installed are listed together and pointed at `install`. The preview shows each package's source; `--dry-run`, `--yes`, `--json`, `--offline` behave as elsewhere. Build options from the spec (`--source`, `--clean`, `--profile`, ...) need the build system and are not part of this slice. Design in `docs/plan/u7-reinstall.md`.

Logged as a new `reinstall` transaction. Since no version changes, `emrac rollback tx-N` on one is refused with that explanation and a bare `undo` skips reinstall records (it undoes the last transaction that actually changed something).

Verified with 7 new unit tests (source choice for every case incl. the Archive not being consulted unless needed or allowed, rollback refusal, `undo` skipping) and in the podman container with real pacman: deleting `/usr/bin/tree` and reinstalling repaired it from the cached file; after `pacman -Scc` it repaired from the repositories; with an old `tree` installed, the repo ahead and the cache wiped, the reinstall came from the Archive (and `--offline` aborted with the reason instead of upgrading), a multi-package run mixed sources, an unknown name aborted the lot, an AUR package (`downgrade`) whose built files were removed was rebuilt from its checkout, the history shows `reinstall` entries, `undo` targeted the earlier install, and `rollback` refused the reinstall. ## Slice u5 — 2026-10-11 — Arch Linux Archive fetch for rollback

`rollback`/`undo`/`redo` no longer need the package file to still be on disk: when a needed official-package version isn't in pacman's cache, the AUR build dir or emrac's own archive cache, it is looked up in the Arch Linux Archive (`archive.archlinux.org`) and downloaded after you confirm. Planning stays free of side effects: it only makes read-only GETs of the package's Archive directory listing, finds the exact `<name>-<version>-<arch>.pkg.tar.*` file (same exact-shape matcher as the local scan; `%3A`-encoded epochs decoded; `.zst` preferred; `.sig` ignored), and the preview gains a "Will download from the Arch Linux Archive" section (also in `--json` as `downloads`). ## Slice u4 — 2026-10-11 — redo

`emrac redo` re-applies the most recent rollback. It is the same code path as `rollback`: reversing a rollback record is a redo, so `rollback_of` now reads as an *active* reversal (a committed rollback that hasn't itself been reversed), and reversing an undo makes the original transaction rollbackable again — undo/redo/undo/redo toggles consistently, and a second `redo` in a row reports there is nothing to redo instead of undoing the first. A downgrade record's inverse is an upgrade (from the newer file the original upgrade left in the pacman cache). `emrac rollback tx-<id of a rollback>` does the same as `redo` for that one. Output reads `redo tx-1 (by reversing tx-2)`; a rollback attempt that failed is neither redoable nor counts as reversing, so re-running `undo` finishes it. Design addendum in `docs/plan/u4-rollback.md`.

Verified with 4 new unit tests (redo of an undo, redo of a downgrade incl. the package-moved-on skip, the undo/redo/undo candidate toggle, failed rollbacks ignored) and in the podman container with real pacman: upgrade → undo (downgrade) → redo (upgrade) → redo again (nothing to redo) → undo → redo, plus install ripgrep → undo → redo; `redo --dry-run` changed nothing; `history` shows the chain.

## Slice u4 — 2026-10-11 — rollback and undo

New `emrac rollback [tx-N]` and `emrac undo` reverse a recorded transaction: an `install` is undone by removing what it installed (`pacman -R`), a `remove` by reinstalling the recorded version, an `upgrade` by downgrading to the previous version (both via `pacman -U` on files already on disk — pacman's `CacheDir` and `~/.cache/emrac/build/<pkg>`; nothing is downloaded). A bare `rollback` and `undo` pick the most recent transaction that is neither a rollback nor already rolled back. Honors `--dry-run`, `--yes` and `--json`.

Safety rules: a package is only touched if it is still as the transaction left it (same version after an install/upgrade, absent after a remove); everything else is listed as left alone with the reason, which also makes rolling back a *failed* transaction reverse exactly the part that landed. If any needed package file is missing the whole rollback aborts before prompting and names every one. Rollbacks are themselves logged (`rollback_of`), `emrac history` shows `rollback of`/`rolled back by`, and rolling back a transaction twice, is refused (reversing a rollback is `redo`, added next). Undoing an install does not cascade: if something now depends on the packages, pacman refuses and the failure is recorded. AUR versions are not compared for the post-state check since RPC metadata can differ from what a VCS package's build produced.

Schema: `PlannedPackage.previous_version` (filled for upgrades) and `TransactionRecord.rollback_of` are new, both optional so u3 logs still parse. Upgrade records written by u3 lack the previous version and are refused with an explanation; old install/remove records work. New `PlanAction::Downgrade`. Design in `docs/plan/u4-rollback.md`.

Verified with 16 new unit tests (inverse for each action, post-state skips, failed-partial, AUR version handling, missing files aggregated, old-format and repeat refusals, candidate ordering, id parsing, exact package-file matching) and inside the podman container with real pacman: upgrade of an Archive-fetched old `tree` then `undo` restored 1.8.0-2 (file found in the AUR build dir); a second `undo` and `rollback tx-1` were refused; `remove` then `rollback` reinstalled from the pacman cache; an `install` of `ripgrep` was undone; rolling back an upgrade whose package was since removed was skipped with a reason; after `pacman -Scc` a rollback aborted naming `tree 2.3.2-1`; `--dry-run` recorded nothing; `history` shows the markers. Not covered by a live test: a rollback of a `failed` transaction (unit-tested only) and `redo`.

## Slice u3 — 2026-10-11 — transaction history

Executed `install`/`remove`/`upgrade` transactions are now recorded in an append-only JSON Lines log at `~/.local/share/emrac/history.jsonl`, and `emrac history` (alias `emrac transactions`, per `SPEC.md`) shows them newest-first with `--limit N`, `--since YYYY-MM-DD` and `--json`. Each record holds an id (`tx-N`), a UTC timestamp, the action, the planned packages, a `committed`/`failed` status and, on failure, the error text. This is groundwork for `rollback`/`undo`/resume, which are not built yet.

Decisions: only transactions that actually ran are logged (dry runs, declined confirmations and empty plans are not); a failed history write only warns on stderr and never changes the transaction's own result; a record is the *plan* that was executed, so a run that failed halfway (official part done, AUR build failed) is one `failed` record rather than per-package status; reading skips unparsable lines so one bad line can't brick the command. Dates use a small tested civil-date conversion instead of adding `chrono`; all times are UTC. Design in `docs/plan/u3-history.md`.

Verified on the host with a scratch `$HOME`: empty history, `--json`, `--limit`, `--since` (including a day with no matches), invalid dates like `2026-02-30` rejected, a hand-written log containing a corrupt line, and `install --dry-run` writing nothing. 10 new unit tests cover the log and date logic.

Verified inside the podman container (real execution): a real `install` and `remove` of `ripgrep` each wrote a `committed` record (`tx-1`, `tx-2`, correct JSON incl. `--json --limit 1`), `remove --dry-run` wrote nothing, and with a stale `/var/lib/pacman/db.lck` forced, `install` failed in `sudo pacman` and wrote a `FAILED` record with the error text while the command still reported its own error. (A removal pacman rejects at the `--print` planning stage, e.g. `remove ncurses`, never executes and so is correctly not recorded.)

Build note: the debug binary was linked against nix's glibc loader because `~/.nix-profile/bin/cargo` precedes `/usr/bin` on this machine's `PATH`, so it can't run in the Arch container or even directly on the host. Build with `PATH=/usr/bin /usr/bin/cargo build` for a binary with the standard `/lib64` loader.

## Slice u1 — 2026-10-11 — config file

New `emrac config` command group (`show`/`get`/`set`/`unset`/`edit`/`validate`) backed by `~/.config/emrac/config.toml` (new `emrac_core::Config`, `toml` dependency). It persists defaults for flags that already exist: `[flags]` (`offline`, `yes`, `dry_run`, `json`, `quiet`), `[review]` (`skip_pkgbuild`, `skip_diff`) and `[search]` (`limit`, `official`, `aur`) — a fixed 10-key allowlist, type-checked on `set`. ## Slice i1 — 2026-07-17 — `db75c7a` — `upgrade`, completing the core CLI loop milestone

Last piece of the `i1 → r1` milestone bar (`search`/`info`/`install`/`remove`/`upgrade` against official repos + AUR, `SPEC.md` Part X). Built almost entirely by reusing what `install` already had rather than a parallel implementation: the AUR PKGBUILD/diff review flow (`review_aur_package`, extracted from `commands/install.rs` into shared `commands/aur_review.rs`, since "upgrade an AUR package" and "build it for the first time" are literally the same `AurBuildBackend::sync` outcome check) and `install_official`/`build_aur` execution paths.

AUR packages: full-upgrade enumerates installed "foreign" packages via new `AlpmBackend::foreign_package_names` (local db packages absent from every sync db — the `pacman -Qm` definition, done via libalpm instead of a subprocess), batch-checks their latest versions in one AUR RPC call (new `AurBackend::info_multi`, repeated `arg[]=` params), and compares with the newly-confirmed-exported `alpm::vercmp`; only the ones actually behind go through the review/build sequence.

- `man pacman`'s wording ("`--print`: only print the targets instead of performing the actual operation (sync, remove or upgrade)") suggested `-Syu --print` would stay root-free like `-S <pkg> --print` already is. Fixed by dropping `-y` from the preview (`resolve_full_upgrade` now runs `-Su --print`, working off whatever's already cached — same "may be a little stale" caveat every other preview already carries); the real upgrade still does a genuine `-Syu`.
- A named package that isn't installed was reusing `remove`'s `PackageNotInstalled` error, so `emrac upgrade nonexistent` said *"nothing to **remove**"* — wrong verb entirely. New dedicated `Error::PackageNotInstalledForUpgrade`, pointing at `install` instead.

`Plan` gained a third `PlanAction::Upgrade`; sizing needed its own small assembly step in `sources.rs` (`official_upgrade_packages`) since upgrade needs the *net* delta (new size − old size, can be negative) rather than install/remove's flat sign-based approach. ## Slice i1 — 2026-07-17 — `6c1d2b2` — AUR building for `install`

`install` now handles the AUR, not just official repos, closing the gap `backend/README.md` had flagged since the install/remove increment. New `AurBuildBackend` (`crates/emrac-core/src/backend/aur_build.rs`) is the only module that shells out to `git`/`makepkg`: each AUR package gets a persistent checkout under `~/.cache/emrac/build/<pkg>`, reused across runs so a rebuild only needs reviewing what changed rather than the whole PKGBUILD again. ## Slice i1 — 2026-07-17 — `fb43285` — Conversational messages, voiced by category

Follow-up to the not-found fix below, after more hand-testing feedback: every user-facing message should read like an actual explanation, not terse technical text, and different message *types* should sound different rather than one generic prefix everywhere.

Landed in two passes: first a blanket `"emrac says: {err}"` wrapper in `main.rs`, then split into a real per-category voice — `emrac says:` for genuine failures, `emrac found:` for lookup outcomes (including not-found), `emrac warns:` for non-fatal AUR degradation, `emrac notes:` for neutral status (aborted, nothing to do).
