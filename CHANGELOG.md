# Changelog

All notable changes to Emrac are recorded here, newest first. Each entry lists the date, the commit it corresponds to, and what changed and why.

Emrac uses **Slices** instead of semver, in three tiers that cycle per release:

- **Slice i\<N\>** — incubation for release `r<N>`: work-in-progress leading up to that release (code, docs, planning — not code-only).
- **Slice r\<N\>** — major release versions (`r1`, `r2`, ...).
- **Slice u\<N\>** — update cycle versions within a release; resets to `u1` at the start of each new `r<N>`.

The cycle repeats every release: `i1 → r1 → u1 → u2 → ... → i2 → r2 → u1 → u2 → ... → i3 → r3 → ...`. `i1 → r1` ships once the core CLI loop MVP (`search`/`info`/`install`/`remove`/`upgrade` against official repos + AUR, per `SPEC.md` Part X) is complete and verified; later `i<N> → r<N>` transitions are a per-release judgment call.

(See `SPEC.md` Part X for the milestone philosophy this follows.)

## Slice u8 (after r3) — 2026-10-19 — `override` and `divert`

pacman puts a package's files back exactly as shipped on every upgrade **and** reinstall: measured in a container, `4750 nobody:users` came back as `755 root:root` although the content was identical, and a local edit of a plain file was replaced even when upstream's file was unchanged. From dpkg (`dpkg-statoverride`, `dpkg-divert`), which pacman has no counterpart for, built on an Arch mechanism: **`emrac override set <path> --mode 4750 --owner root --group wheel`** keeps the mode and owner; **`emrac divert add <path>`** keeps your own version of a packaged file (not a `backup=` file, for which pacman has `.pacnew`). The policy is `/etc/emrac/policy.toml`; a pacman hook runs `emrac policy-helper apply` after each transaction that touches a policy path (override: `chmod`/`chown` through an open descriptor; divert: three sha256 sums decide, the package's from pacman's own `mtree`, the file now, your stored copy), and a second pre-transaction hook saves an edit of a diverted file before pacman can overwrite it. `override list|remove`, `divert list|remove|diff|reviewed`, `policy status|apply`; `check` treats an overridden mode and a diverted file as expected; plans list the policy they touch.

**The risk, and what is done about it.** A diversion freezes the file: the package's fixes for it, security fixes included, never take effect, and pacman reports a normal upgrade. So: `divert add` asks (default no; `--yes` does not answer; `--allow-stale` opts in; the root helper refuses without it), with extra warnings for setuid files and compiled programs and libraries; each diversion records the package's checksum and version at the time, and when the package ships a different file it is **stale**: pacman's own output says so after every such transaction, `divert list`/`policy status` mark `STALE`, `doctor` has a row, plans warn by name before the upgrade (exact when the new package is cached), and `divert diff` shows what you are missing, `divert reviewed` records that you looked. Root runs `emrac` from a hook, so the helper writes the hook only for `/usr/bin/emrac` or `/usr/local/bin/emrac` owned by root with root-owned, unwritable parent directories, and acts on a policy file only if every directory down to it is root's and closed to others (checked when written and at each apply). Found by the container run: putting a diverted file back after its package is removed makes the package impossible to install again (the file already exists), so it now waits in the store and returns on the next install; and an edit made between transactions is lost unless a pre-transaction hook saves it. New: `policy.rs` (27 tests), `policy_ops.rs`, `policy_preview.rs` (4), `dev/e2e/policy.sh` (47 checks against real pacman), `docs/design/local-file-policy.md`.

## Slice u3 (after r3) — 2026-10-18 — `emrac explain`

`emrac explain <pkg>` shows how the source-or-binary recommendation of `recommend` was reached, not only the verdict: every rule that applied, in the order the engine applied it, with its points (or the cap it sets), what was found and **where the input came from**; the total before and after the cap; and *what would change this*, worked out by running the same engine again with one input changed (`-march=native`, `-O3`, a quick build, a package that changes rarely, enough memory and disk, three measured builds) and showing only the changes that alter the score, the verdict or the confidence. Nothing is computed twice or by a second set of rules (`recommend::explain` calls `evaluate`). `--json` carries the facts, the rules and the alternatives. `recommend` now says `emrac explain <pkg>` where it used to say "N more". New: `recommend::explain` (5 tests), `commands/explain.rs` (4), a command-line test, 4 checks in `dev/e2e/final-check.sh` (59 of 59 now). Slice numbers: u3 was planned before u4 to u7 and built after them.

## Slice u7 (after r3) — 2026-10-18 — remove the tools an AUR build installed only to build

`makepkg -s` installs an AUR package's build dependencies and never removes them, so compilers, `cmake` and the like pile up. emrac now knows what was installed before the build, so at the end of a run that built AUR packages it names exactly the packages the builds added as dependencies that nothing else needs: libalpm's `required_by` and `optional_for`, then a fixpoint (`cmake` goes, and the library only it needed; `python` stays if the package just built requires it). New setting `build.remove_make_deps`: `ask` (the default; lists them with their size and asks, `--yes` never answers it and prints the command instead), `always`, `never`. The removal is an ordinary `emrac remove` (plan, pre-flight, journal, history), so `emrac undo` brings the tools back. Works for `install`, `upgrade`, `rebuild`, `reinstall`. Two things found by the container run: the offer must wait until the command's own transaction is finished (the journal allows one at a time), and the removal needs a fresh libalpm handle (the one in use did not know the build tools). New: `build_tools.rs` (6 tests), a config test, `dev/e2e/buildtools.sh` (9 checks), `docs/design/build-tools.md`.

## Slice u6 (after r3) — 2026-10-18 — what pacman leaves behind when a transaction fails

When a transaction fails or is cut off, emrac now looks at the packages it named and says which ones pacman still lists although files are missing, with the command that mends each. Found by failing pacman on purpose in a container (a file of the package made to fail with "no space left"): pacman reported "no packages were upgraded", yet the package was recorded as installed, its install script had run, and a file was missing; nothing told the user. Now: `emrac warns: pacman lists phantom 1-1 as installed, but 1 of its 2 files is missing (usr/share/phantom/a.txt)` and `to mend it: emrac reinstall phantom`; for a removal that stopped halfway, `emrac remove <pkg>`. Config files (`backup=`) and what `NoExtract` leaves out are not counted. It also runs when `history recover` finds a cut-off transaction. New: `reconcile.rs` (2 tests), `dev/e2e/recovery.sh` (9 checks: the install fails, pacman still lists the package, emrac says so and names the fix, the fix works, a successful transaction says nothing).

## Slice u5 (after r3) — 2026-10-18 — `.pacnew` and `.pacsave` preview

`upgrade`, `install` and `remove` plans now list the config files you changed that the plan will leave beside your edits, instead of leaving you to find the `.pacnew` afterwards. The rule is pacman's three-way comparison (the md5 recorded at install, the file now, the file in the new package), checked against real pacman in a container for every case before it was written down: an untouched file is replaced silently; an edited file gets a `.pacnew` only if the new package changes it (not if it is unchanged upstream, or already identical to yours); a file you deleted is just written; `NoUpgrade` always leaves a `.pacnew` for a file that exists, even an identical one; a file the new package stops shipping is kept as `.pacsave` if edited; a removal keeps an edited file as `.pacsave`. When the new package is already in the cache its file is compared exactly (certain); otherwise an edited file is listed as a maybe and says why. `--json` gets a `config` list. New: `config_preview.rs` (7 tests), `plan_preview.rs` (hooks and config effects travel together and stay out of the plan id), `Extracted::path`, 12 checks in `dev/e2e/preview.sh` (22 of 22 now), `docs/design/config-preview.md`.

## Slice u4 (after r3) — 2026-10-18 — hook preview

`install`, `remove` and `upgrade` now list the pacman hooks the plan will run, before the transaction and after it, in the order pacman runs them, and say which would stop it: an `AbortOnFail` hook, or one whose `Depends` is not installed, cancels a transaction the user had already confirmed, and pacman shows none of this until it happens. The rules (directories and overrides, order by name without `.hook`, glob targets where `*` also matches `/`, negation, install versus upgrade of a path, hooks a package brings with it) were written from `alpm-hooks(5)` and confirmed by running probe hooks in a container (`research/alpm-hooks.md`). The hooks are not part of the plan or its id. File lists of packages not yet installed come from `pacman -Fy`; without them the preview names the packages it could not check and does not guess. `--json` adds a `hooks` object. New: `hooks.rs` (14 tests), `dev/e2e/preview.sh` (10 hook checks: the predicted hooks equal the ones pacman ran for an install, a removal and a full upgrade), `docs/design/hook-preview.md`. Also: the pacman truth table of `research/vercmp.md` is pinned as a test.

## Slice u2 (after r3) — 2026-10-16 — `emrac recommend`

`emrac recommend <pkg>` (and `recommend source <pkg>` / `recommend binary <pkg>` for one side) says whether a source build is worth it on this machine: a Source Suitability Score from 0 to 100, a verdict (binary, source, either, or source as the only option), a confidence, the build time here and the reasons that weigh most. The rules are stated in `docs/design/recommend.md` and the engine is pure (`recommend.rs`): the gain (do your makepkg flags differ from the repository's? with Arch's defaults the score is capped at 30; `-march=native` or a supported x86-64-v3 or v4 target adds 25; `-O3` adds 5), the cost (a measured build time or an estimate shown as a range), how often the package changed in your history, trust, and whether the machine has the memory and disk. Every build emrac runs (`build`, AUR `install` and `upgrade`, `rebuild`) is now timed into `~/.local/share/emrac/build-times.jsonl` (newest 500 lines), and a measured time replaces the estimate. `info --json` of an AUR package gained `make_depends`. Advisory only: `install` and `upgrade` do not use it yet. 18 engine tests, 2 more command-line tests, 5 container checks. Plan: `docs/plan/r3/u2-recommend.md`.

## Slice u1 (after r3) — 2026-10-16 — self upgrade for copies no package owns

`emrac self upgrade` and `self downgrade` no longer refuse a copy installed with `cargo install` or put in `~/.local/bin` or `/usr/local/bin` by hand, when its folder is writable by you: they update it **in place**. The release is downloaded and checked as before, built with `cargo` (no `makepkg`, `pacman`, `sudo` or `fakeroot`), the new binary is run from its staging folder and again from the folder it is going to, the old file is kept in `~/.local/share/emrac/self/previous/` (newest 3), and the new file is renamed over the old one in one step. A new binary that does not report the target version is refused before anything changes, or, after the rename, replaced by the kept file automatically. The packaged copy is updated through pacman exactly as before; another package's file, a `target/` build, a link, an unknown owner and a folder you can't write to are still refused, and emrac never asks for root to do this. `--dry-run` shows the `Method:`; the plan is `docs/plan/r3/u1-in-place-update.md`, the page `docs/design/self-upgrade.md`.

## Slice u2 (after r2) — 2026-10-14 — license: GPL-3.0-or-later

emrac is now licensed under the GNU General Public License, version 3 or any later version. The choice follows from the dependencies: the `alpm` and `alpm-sys` crates are GPL-3.0 and libalpm is GPL-2.0-or-later, so the program as distributed has to be GPL-compatible, and the other 136 dependencies (MIT, Apache-2.0, ISC, BSD, Unicode, CDLA-Permissive-2.0 and similar) are permissive licenses that can be combined with GPL-3 code (a reading of the license names, not a legal review). `LICENSE` holds the standard text from gnu.org (checked against its published SHA-256), the workspace `Cargo.toml` sets `license = "GPL-3.0-or-later"` for both crates so `cargo metadata` and the packages carry it, and the README and the project page say so. The `r2` tag was made before this and does not contain the license; a package built from that tag would have none, so the source for the first AUR package is tagged `r2-aur` ("Emrac First AUR Release"), cut from a commit that includes it. The program's behaviour is identical to `r2` and the version stays `0.2.0`; the Rust code differs only in tests (see the next two entries) and the license lines in the `Cargo.toml` files. The notes are `docs/releases/r2-aur.md`, which is also the text of the tag.

## Small change (after u9), ledger events can be acknowledged — 2026-10-15

`emrac ledger events --ack` marks other programs' events as seen, all of them or only the ids given (`--ack ev-1a2b3c4d5e6f`). Each event now has a stable id (a hash of its time, key, action, program and paths) shown in the list. Tests: the id is stable and tells events apart; an acknowledgement is chained, not repeated, and the chain still verifies.

The "Updating" row of `emrac self check` and `self diagnose` still read "emrac does not update itself yet": text from u11, written before `self upgrade` existed, never updated. ## Fix (after r3) — 2026-10-16 — the command-line tests no longer see makepkg's package folder

The first real `emrac self upgrade` to r3 on the developer's machine failed in `check()` with two failing integration tests (`the_sandbox_hides_the_network_secrets_and_home_from_a_build` and `a_runaway_build_is_stopped_by_its_limits_and_the_reason_is_named`): "A package has already been built" and "a package was built". Cause: `self upgrade` runs `makepkg` with `PKGDEST` and `SRCDEST` set to its staging folder, so that the checked tarball is the one used; `check()` inherits them, and the tests' own sandboxed `emrac build` of a fixture then wrote its package to that shared folder, where the next test found it. The same would happen to anyone building with `PKGDEST` set (many AUR helpers do). The tests' command helper now removes `PKGDEST`, `SRCDEST`, `SRCPKGDEST`, `LOGDEST` and `BUILDDIR`; the two tests pass with those variables set, which the first version of them did not. The failed run also showed that its staging folder was not removed: the fixture left a folder with no permissions in it, and a plain removal stops at the first one. The staging folder is now removed after widening permissions (`remove_tree`, tested with an unreadable tree). The `r3` tag keeps the old tests, so `emrac self upgrade --skip-tests` is the way to upgrade to it with `self upgrade`; a build in a clean chroot (no such variables) passes, as the AUR package does. The fix goes out with the next release.

## Slice u20 (after r2) — 2026-10-15 — trust and the safety net

Plan: `docs/plan/r2/u20-trust.md`. Design for users: `docs/design/trust.md`. Five parts, one commit each.

1. **AUR trust signals.** The review of an AUR package, and `emrac info`, now show rule-based signals from the AUR's data and the change since your last build: a name one letter from an official or installed package (or the same words reordered), a binary repackaging of an official package, claiming an official package other than its own base, orphaned, first submitted under 30 days ago, few votes, flagged out of date, and the **high** ones: the maintainer changed since you last built it, the sources or checksums changed under the same `pkgver`/`pkgrel` (from the old and new `.SRCINFO`), the signing keys (`validpgpkeys`) differ from the pinned ones; also a source from a new host. A high signal asks the default-no question (`--accept-risks` passes it, `--yes` does not). Kept in `~/.local/share/emrac/aur-trust.json`, written when the build is installed.
2. **The Arch news gate.** `emrac news [--all]`, `emrac news ack`; the unread news under every upgrade plan; critical news stops the upgrade (`--ack-news` or `news ack` to go on), the rest only warns. Critical means risk, as the developer put it: a breaking change or manual intervention in the text, or a title touching the kernel and initramfs, the bootloader, the C library and toolchain, systemd, pacman and its keyring, OpenSSL, graphics drivers and firmware, or the filesystem layout. `safety.arch_news = gate | warn | off`. Run on the real feed it classified ten items, among them "Mkinitcpio >=42 requires manual intervention…" as critical (manual intervention; kernel or initramfs) and "Active AUR malicious packages incident" as news only.
3. **Protecting pacman's database.** A backup of `/var/lib/pacman/local` (newest 3, `mtree` left out, 6 MiB) before each transaction, `pacman -Dk` before and after, the restore command printed if a transaction left it inconsistent, a running pacman or a leftover lock in the pre-flight, a `doctor` row. `safety.db_backup = on | off`.
4. **Repository trust.** A plan that would install an older version than the installed one is a pre-flight problem (it caught `emrac install quickshell-git` planning 0.3.0 over 0.3.2); a repository database more than a day older than the newest ever seen is a warning in the pre-flight and in `doctor`.

## Slice u7 (after r2) — 2026-10-15 — a history that can be archived, acknowledged and checked

The history was "append-only" by convention only: the file is yours, so anything running as you could edit it and emrac would not notice. Now every line links to the one before it. ## Slice u6 (after r2) — 2026-10-14 — emrac's voice

emrac now says what kind of statement a line is. Before, 57 lines began `emrac notes:` whether emrac knew a thing, believed it, or was guessing. There are twelve verbs: **says** (broke underneath), **found** (a fact to act on, or a result heading), **notes**, **plans**, **asks**, **warns**, **suspects** (weak evidence, may be wrong), **thinks** (a judgment with reasons, not proof), **suggests** (the next step), **refuses** (nothing overrides it), **confirms** (checked or done, and holds) and **remembers** (recalled from what you did). Where they landed: a build that failed because the sandbox has no network is now `suspects` ("its output mentions a host it could not resolve") before the retry question; the dependency-conflict explanation and the `pacnew` class reasons are `thinks`; every `doctor` fix and the follow-up after a `pacnew` change is `suggests`; things that were done (`config set`, `pin`, `snapshot`, `pacnew` apply and revert, `cache clean`, a built package) `confirm`; a PKGBUILD that changed since you last reviewed it is `remembers`; audit findings take the voice of the worst one (a warning `suspects`, a high-risk finding `warns`, a critical one `refuses`); a prompt that gets no answer because the input is closed now says `emrac refuses: no answer came (the input is closed), so nothing was changed.` once, instead of changing nothing in silence. Errors keep `found` and `says` exactly as documented, so scripts that read them still work; exit codes and `--json` are unchanged. Problems and doubts (`says`, `warns`, `suspects`, `refuses`) go to stderr, results to stdout (an audit's report stays on stdout). The verb is coloured on a terminal, and not when piped, with `NO_COLOR` set, or under `TERM=dumb`.

One `Voice` type in the core library carries the verb, the stream and the colour, and `say!` prints it; nothing builds an `emrac <word>:` prefix by hand any more. Two tests keep it that way: one scans every source file for a hand-built prefix, the other for a hedge word (`probably`, `looks like`, `may be`, …) in a `says`, `found` or `confirms` message — each checked by planting an offender and watching it fail. 100 prefixes were migrated mechanically and about twenty messages given a different voice by hand; the one integration test that asserted on a message (`emrac manifest:` became `emrac found:`) and the end-to-end check for `emrac built` were updated. Seen in a container against a real pacman: a plan, an install declined by a closed stdin (`asks`, then `refuses`), `snapshot`, `pin`, `unpin`, `verify`, `history`, `cache stats`, `doctor` and a package that does not exist; on a pseudo-terminal the verb is green for `confirms` and the plain text when `NO_COLOR=1` or piped.

Not done: plan warnings built in the core library (the removals and dependency-conflict warnings in a plan) are still all `warns`; the messages inside `--json` keep their wording; the voice of a message cannot yet be set from the core (a message carries text, not a verb).

## Slice u30 — 2026-10-14 — `pacnew`: checked before it is applied, recorded, and revertible

`emrac pacnew` could replace a config file but never checked that the new one works (the stock `mirrorlist.pacnew` has every `Server` line commented out: taking it leaves pacman with no mirrors), kept backups nothing used, and left a merge with conflicts to be kept or skipped. **Validation:** before a take, merge or edit is written, the candidate is checked — `visudo -cf` for sudoers, `sshd -t` for sshd_config (both through `sudo`), `pacman-conf --config` for pacman.conf, `findmnt --verify` for fstab, at least one uncommented `Server` for the mirrorlist, a JSON parse for `.json`, `bash -n` for the shell-sourced files (`mkinitcpio.conf`, `makepkg.conf`, `default/grub`); files without a checker say so. A failed check refuses that file and shows the tool's message; there is no override, the way past is to edit the file, which is checked again. **Record and revert:** every change appends to `~/.local/share/emrac/pacnew-log.jsonl` — `started` before anything happens, `done` or `failed` after, so a crash leaves a visible half-finished entry — with SHA-256 of the live file before and after, its mode and owner, and the paths of the copies, now of both the live file and the `.pacnew`. ## Slice u29 — 2026-10-14 — a lean cache

After the first `cache clean`, pacman's cache still held 7.3 GiB, of which 6.95 GiB were just the installed version of each package (pacman keeps whatever it downloaded; only an offline `reinstall` or `redo` reads them) and 2.17 GiB previous versions. `emrac cache clean --lean` (also on `trim`, `stats`, `list`, or `cache.policy = "lean"` in the config) keeps one canonical rollback set instead: the old versions needed to undo anything done in the last `cache.keep_days` days (default 14; the newest change counts however old), counting only what each record really changed and whatever its status; AUR builds (installed and previous — the Archive has none); the installed file of a package whose version is no longer in the repositories (a pinned or not-yet-upgraded package: the mirrors moved on); and any version newer than the installed one (a pending upgrade). **Two things the real data corrected.** The plan said "the last K transactions". ## Slice u28 — 2026-10-14 — `emrac cache`

After the first real upgrade `~/.cache/emrac/build` held 14 GB and pacman's cache 7.3 GB, with nothing to look at or trim them. `emrac cache` (also `cache list`) and `cache stats` break the caches into the four categories `SPEC.md` names — **source** (downloaded tarballs, zips, `.deb`s and VCS clones in build folders), **build** (each build folder's `src/` and `pkg/`), **binary** (built package files and packages fetched from the Archive) and **package** (`/var/cache/pacman/pkg`) — with sizes, the largest packages and how much `clean` would free. `cache clean`, `cache trim --size-limit` and `cache purge` change them. AUR checkouts (`.git`, `PKGBUILD`, `.SRCINFO`) are never cache: deleting them would forget what was reviewed.

**What `clean` keeps.** The installed version of a package and the newest older one (so `downgrade` and `undo` work), any version *newer* than the installed one (a pending upgrade, such as what `--inspect` downloaded), and any version named by the last 20 recorded transactions (so `undo`/`redo` of them works). Everything else goes: build trees always, package files of other versions and of packages no longer installed. Sources go only when named (`cache clean source`) and only when 30 days old, because some cannot be downloaded again by a program (the ST zip that needs a login). `purge` ignores the protections and says what that costs; with no scope it needs `--force`. `trim` removes the oldest of what `clean` would until a category fits, and stops there — it will not touch protected files to reach the limit.

**Safety.** `--dry-run`/`-n` lists every path with its size and the reason it stays or goes; otherwise a per-category summary is confirmed (default no; `--yes` answers; a closed stdin declines). Paths must lie under `~/.cache/emrac` or pacman's cache directories; symlinks are removed, never followed; read-only directories (Go module caches) are made writable before removal; pacman's cache is left alone while its database lock exists and its root-owned files go through `sudo rm`, with their `.sig` files, in batches. Scopes are given as words or letters (`source|s`, `build|b`, `binary|n`, `package|p`) or as `--source` etc.; the short forms are fixed (`cache l/s/c/p/t`, `cc`, `cs`, `-o`, `-m`, `-n`, `-f`), no prefix matching. `-n` is now also the short form of the global `--dry-run`.

Verified with 8 unit tests (file-name parsing; durations, sizes and scopes including rejects; installed and previous kept, newer kept; a recorded version kept; purge, trim stopping at the limit and never reaching a protected file; `--older-than` and the 30-day source rule; deletion only under the roots; a tree with a read-only directory and an outward symlink removed without touching the target) — 233 core, 18 CLI integration, 9 CLI unit. In the container, as root: `--dry-run` and a closed stdin change nothing; `cc -y` removes the build trees (the outward symlink's target survives), the built file, the archive file, an old cached version and an uninstalled package, and keeps the installed, previous and newer versions; `cache c s -y` removes only the old source; `purge` with no scope, a bad scope and a bad duration are refused with a reason; `trim` finds nothing it may remove. As a non-root user with a sudo rule for `rm`, a root-owned cache file and its `.sig` were removed through `sudo`. On this host `cache list` reports 20.9 GiB and `clean` would free 10 GiB (the build trees); no real clean was run there.

**Found on the first real run:** `cache clean --dry-run` printed every kept file too (about 1,350 lines on this host), burying the 48 that would go. A dry run now lists only what would be removed and summarizes the rest by reason (`1048 files, 6.95 GiB — the installed version`); `-v` lists each kept file. Cleaning the archive cache also removes the old packages `emrac pacnew --fetch` downloaded; it fetches them again when needed.

Not built: `cache verify`, `export`, `import`, the interactive manager (`-i`), `emrac cleanup --cache`/`gc`, automatic cleanup after upgrades, a custom `SRCDEST`, deleting by package name. Design in `docs/plan/r1/u28-cache.md`.

## Slice u27 — 2026-10-14 — `emrac pacnew`: your edits told from upstream's

After the first real upgrade five `.pacnew` files were waiting and `emrac doctor` could only say so. `emrac pacnew` lists them and sorts each by comparing three texts: the version the *old* package shipped (base), the live file (ours) and the new one (theirs). The base comes from the owning package's earlier versions in `pacman.log`, read from the pacman cache or (with `--fetch`) the Arch Linux Archive; if the live file is exactly what some earlier version shipped it was never edited (`untouched`); if the new file equals the base only you changed it (`mine-only`); if both differ it is `both-changed` and a `git merge-file` three-way merge is tried (shown as a diff against the live file, never written when it has conflicts); `identical`, `pacsave` and `unknown` (no base readable; the reason says why and mentions `--fetch`) complete the table. A `.pacnew` older than the installed package's recorded md5 is `unknown` rather than trusted.

`emrac pacnew diff <file>` prints what you changed, what upstream changed and how a merge comes out. `emrac pacnew resolve [file…]` offers keep / take / merge / skip per file: an empty answer, `--yes` and a closed stdin all skip, `--dry-run` only says what it would do, `--json` prints the findings and asks nothing. Taking or merging first copies the live file to `~/.local/share/emrac/config-backups/<unix-time>/…` (mode 0600), then changes it through `sudo` (`mv`, or `install` with the live file's mode and owner for a merge); files that can lock you out (`sudoers`, `passwd`, `fstab`, `pam.d/*`, `sshd_config`, …) also need their path typed. ## Slice u26 — 2026-10-14 — dependency conflicts that stop an AUR build are explained

Found on a real upgrade, not by a test: the installed `mangowm-git` required the package *name* `scenefx0.5` (an old AUR package); the new `mangowm-git` needs `scenefx` from `extra`, now 0.5-1 and providing the same `libscenefx-0.5.so`, and the two conflict. makepkg's dependency step asked pacman for `scenefx`, pacman asked "Remove scenefx0.5?", then refused ("removing scenefx0.5 breaks dependency 'scenefx0.5' required by mangowm-git") and emrac printed only "the build failed in the dependencies and sources step (exit status: 8)". My first advice — answer *y* because the soname matches — was wrong: a dependency on a package name is not met by a matching `.so`.

**Diagnosis.** When the dependency step fails, emrac reads the checkout's `.SRCINFO` (`depends`, `makedepends`, `checkdepends`), takes those that are missing and available from the repositories, and runs the u24 libalpm simulation as an install. If preparing it fails with unsatisfied dependencies, the failure is paired with the conflict removal that caused it and reported as a `DependencyConflict`: which package would go, who still requires it, which package conflicts, and what the removed package provides that the replacement does or does not also provide. No pacman text is parsed.

**Offer, not action.** If the replacement provides everything the removed package did, emrac prints the explanation and the two commands (`sudo pacman -Rdd <old> && sudo pacman -S <new>`) and asks "Swap … now, then continue building …?" — default no, not answered by `--yes`, silence is no. Yes runs them through `sudo` with pacman's own questions and builds again; if the second command fails after the first succeeded, the error says what is now missing and how to put it back. ## Slice u20 — 2026-10-14 — resource limits for sandboxed builds

The sandbox hides things from a build; now it also bounds what a runaway or hostile build can consume. Four limits, all applying to the two sandboxed `makepkg` steps (the host step that installs dependencies and fetches sources needs `sudo` and the network and stays outside; `--no-sandbox` builds have no limits, which is what the flag means): **memory** (a cgroup `MemoryMax` of 75 % of total RAM, swap disallowed), **processes** (`TasksMax` 4096, which stops fork bombs), **size** of the build's `/tmp` and `$HOME` tmpfs (`bwrap --size`, 8 GiB each) and **time** (120 minutes, then emrac kills the sandbox and everything inside it). Memory and process limits go through `systemd-run --user --scope`, because bubblewrap has no cgroup support. Configurable with `emrac config set build.timeout_minutes | build.memory_percent | build.max_tasks | build.tmpfs_gib`; `0` turns a limit off. Unlike `--no-sandbox` these may live in the config, since they only restrict a build.

When a limit stops a build the error says which one and which knob to turn: "It hit its memory limit (75% of RAM) and was killed; raise `build.memory_percent`", "It hit its process limit (4096 tasks); raise `build.max_tasks`", "timed out after 120 minutes. Raise `build.timeout_minutes`". If the user manager can't give a scope (no systemd user session, cgroup v1, a container) emrac says so once and carries on with the time and size limits, which need nothing — it never pretends to enforce what it can't. Design in `docs/plan/r1/u20-limits.md`.

Found while testing: systemd's default `OOMPolicy=stop` answers the first OOM kill by terminating the whole scope, leaving nothing to report, so the scope uses `OOMPolicy=continue`. And **diagnosing the kill by polling the cgroup from outside cannot work** — the cgroup disappears within milliseconds of its last process exiting, right after the kill — I measured it naming the cause in only 4 of 12 runs, and a first version even latched onto the terminal's own scope. The scope now runs a small wrapper shell that stays inside the cgroup until it has read `memory.events` and `pids.events` itself and hands them over in a file; that is deterministic.

Verified with 8 new unit tests (the `systemd-run` property builder incl. `OOMPolicy` and zero-means-off, `--size` placement, config conversion, the timeout runner killing a real `sleep` on time, the counter parsers incl. the two different `max` lines, the wrapper's exit-status hand-back) and 4 config tests for the new keys, plus 2 CLI integration tests against the real binary (170 core, 16 CLI in total): a build that eats memory without end under a 1 % cap is stopped and named, a fork loop under a 32-task cap is stopped and named, and without a systemd session the warning appears and the build still succeeds (no warning when both limits are off). Measured on real builds: memory kill explained **12 of 12**, fork bomb **6 of 6** with no leftover processes, a 1-minute timeout fired at 62 s with no leftover processes or stray files, and a build allocating 1.5 GB runs normally with the memory limit off. In the podman container (no systemd session) the sandboxed install warns once and installs.

Not done: Landlock as a second layer, a throwaway root hiding the host's installed packages from the build, CPU caps (deliberately: a build should be fast), ccache.

## Slice u19 — 2026-10-13 — sandboxed AUR builds

The build step of every AUR package now runs inside bubblewrap (the design in `docs/design/source-build.md`, with the owner's decisions: host `makedepends` visible read-only, `bwrap` an optional external dependency, **warn-and-ask** for network). `makepkg`'s own flags give the phases (read from `/usr/bin/makepkg` 7.1, then proved by hand): (1) on the host, `makepkg -s --verifysource` installs dependencies and downloads and verifies sources — the only part that needs `sudo` and the network; (2) in the sandbox, `--nobuild --nodeps --cleanbuild` extracts and runs `prepare()`/`pkgver()`; (3) in the sandbox, `--noextract --nodeps` runs `build()`/`check()`/`package()` and makes the archive. An already-built package skips all three.

The sandbox: `--unshare-all --die-with-parent --new-session`, a read-only root, fresh `/dev` and `/proc`, `tmpfs` over `/tmp`, `/home`, `$HOME` and `/run/user`, a writable bind of only the build directory plus any `SRCDEST`/`PKGDEST`/`BUILDDIR`/`LOGDEST` from the user's makepkg config, and a **cleared, whitelisted environment** (`GITHUB_TOKEN`, `SSH_AUTH_SOCK`, `AWS_*`, dbus addresses never reach the build). Same uid, so makepkg's refusal to run as root and `fakeroot` both work. **Network is off** for steps 2–3. If the audit expects network use in `prepare()`/`build()`/`check()`/`package()`, emrac warns and asks — default no, **not answered by `--yes`**; `--allow-network` answers yes; a build that fails with the network denied says so and names the flag. `bwrap` is probed by actually running it with the same mounts as a real run; if it isn't usable emrac **refuses** and says how to fix it, and `--no-sandbox` (a flag, deliberately never a config key) builds as before with a loud warning.

New **`emrac build <target>...`** (a SPEC command): builds AUR packages (same review and audit as `install`) or a local PKGBUILD directory (audited first: critical refuses, high asks) in the sandbox, prints the manifest and the package paths, installs nothing. `install`, `upgrade` and the AUR rebuild in `reinstall` use the sandbox by default and accept `--no-sandbox` and `--allow-network`. Found while testing: the availability probe lied. In a rootless container `bwrap` can create namespaces but cannot mount a fresh `/proc`; a probe without `--proc` reported "usable" and the build then failed halfway. The probe now uses the same mounts as a real run. A host `/proc` is deliberately **not** a fallback — a shared `/proc` would let the build read emrac's own `/proc/<pid>/environ`, defeating the cleared environment. For the test container, `--security-opt 'unmask=/proc/*'` is enough (no capabilities, not `--privileged`); `dev/container/run.sh` passes it and the Containerfile installs bubblewrap. Also: `$HOME` must exist inside the sandbox, so it is an empty tmpfs.

Verified with 6 unit tests of the pure `bwrap` argument builder and environment filter, and a CLI integration test that runs a **real sandboxed build** against a real listening socket (skipped where `bwrap`/`makepkg` can't run; 162 core, 14 CLI in total): sandboxed, the build reaches nothing (0 connections), sees no token or agent socket, a read-only `/etc`, an empty home, and its write to `$HOME` never reaches the host; with `--allow-network` it connects. Inspection is by `bsdtar` (libarchive, already a pacman dependency), reading only — nothing is extracted or executed — and covers the file list with modes, `.PKGINFO`, the packaged `.INSTALL` scriptlet and the few small files whose content matters.

The manifest prints for every AUR build (to stderr): file count, installed size, and a plain summary — install scriptlet and its functions, systemd units, users and groups created, pacman hooks, replaces/conflicts, config files kept. Findings use the audit's severities and policy: **critical** (`/etc/ld.so.preload`, or code in a hook/unit/scriptlet that the script rules rate critical) → refused, no override, the built file is kept and its path given; **high** (setuid files, sudoers drop-ins, cron entries, files in `/home` or `/root`, dangerous code in a hook/unit/profile script/scriptlet) → the default-no prompt that `--yes` does not answer and `--accept-risks` does; otherwise it installs without a further question. Warnings: setgid, enabled-by-default units, `profile.d` scripts, plain pacman hooks (what a hook *runs* is scanned as code and escalates it), files outside the usual directories. The same path serves `install`, `upgrade` and the AUR rebuild in `reinstall` (which gained `--accept-risks`).

`emrac audit <file.pkg.tar.*>` inspects any package file the same way — before a `pacman -U` on something downloaded, or on a cached package. Design in `docs/plan/r1/u17-manifest.md`.

Found while testing: the script rules were quote-aware, so a payload passed as a string (`sh -c 'echo k >> ~/.ssh/authorized_keys'`, `bash -c "curl … | sh"`, `eval '…'`) was never read — in PKGBUILDs and shipped scripts as much as in hooks. The scanner now recurses into `sh -c` and `eval` strings.

Verified with 14 new unit tests against real `bsdtar -tv` output of a makepkg-built fixture (listing parser incl. spaces, symlinks and setuid/setgid/sticky bits; every rule; hook content escalation; verdicts) and 2 CLI integration tests that build package archives (150 core, 12 CLI in total). **Calibration over all 932 official packages in a pacman cache**: no critical finding; the only high findings are 17 legitimate setuid helpers (`fusermount`, `mount.cifs`, `chrome-sandbox`, …); 44 packages ship a hook, which is why a plain hook is only a warning. The PKGBUILD false-positive survey is unchanged by the new recursion. **End to end in the podman container with real `makepkg` and `pacman -U`**, using a local "upstream" under a real AUR name: a benign package builds, shows "nothing here needs your attention" and installs; a package with a setuid file stops (exit 1, `--yes` and a closed stdin both mean no), keeps the built file, and a re-run (makepkg's already-built path) installs it on `y` with mode 4755 on disk; `--accept-risks` installs without asking; a package shipping `/etc/ld.so.preload` is refused, nothing is installed and the file is kept; a hook running `curl | sh` is high and is declined.

Not covered: the manifest does not look inside binaries or archives shipped in the package (it can't tell what an ELF does); official-repo packages are not inspected during `install` (pacman has verified their signatures; `emrac audit <file>` works on them); the rebuild branch of `reinstall` shares the helper but wasn't separately exercised because a previously built file is normally reused.

## Slice u16 — 2026-10-13 — audit coverage

Follow-up to the limits stated in u15. **The rest of the repo is now read**: every file at the audited revision (the PKGBUILD's own git revision — `FETCH_HEAD` for a pending update — so it is what would be built) is classified. Helper scripts (by shebang or extension, plus other `.install`/`.hook` files) get the dangerous-pattern rules at full strength but not the PKGBUILD-only ones, since a shipped wrapper may legitimately use `sudo`; patches are judged by their **added** lines only, capped at warning and labelled "added by this patch"; a committed ELF binary is **high**; other binaries and archives are warnings; docs, licenses, keys, images, fonts and metadata are skipped; files over 1 MiB are noted as unscanned; at most 200 files are read. Directory targets are walked (not `.git`, `src`, `pkg`, built packages); a single-file target looks only at the files beside it.

**More obfuscation is caught**: a file downloaded and run later (`curl -o i.sh …; sh i.sh`, `wget -O i …; chmod +x i; ./i`) is high; unpacking straight into an interpreter (`gpg -d`/`zcat`/`tar -O`/`unzip -p … | sh`) is high; a command spelled with `$'\x..'` escapes is high; a command word built at runtime (`$a$b`, `$(…)`) and long encoded blobs are warnings; `curl … | sh` inside a quoted `os.system(…)`, `exec(b64decode(…))` and the multi-line Python socket + `dup2`/`pty.spawn` reverse shell are caught in non-shell scripts too. Command substitution in top-level assignments (`x=$(curl … | sh)`, which runs when the PKGBUILD is merely read) now reaches the command rules.

**Found by the survey and fixed**: `install=$pkgname.install` — the usual form — was never resolved, so most scriptlets had not been read at all; persistence is now judged by where a command *writes*, not by a path appearing on the line (`grep x /etc/passwd > /dev/null` is no longer a hit); shell startup files are **high** in install scriptlets/shipped scripts (critical in a PKGBUILD) because legitimate packages such as `nvm-git` append a `source` line there, while SSH keys, `ld.so.preload`, sudoers and account files stay critical everywhere (a refinement of the severity table, recorded in the design doc); the command-word reader now handles `case`/`for`, array assignments and `x=$(cmd …)`, cutting `dynamic-command` noise from 39 to 6 and sharpening the other rules. Design in `docs/plan/r1/u16-audit-coverage.md`.

Verified with 14 new audit unit tests (36 in total) and a CLI integration test over a package directory (a clean PKGBUILD and scriptlet with the payload in a helper script, a patch, a binary and an ignored `src/`). **Survey over every file** of 38 current official PKGBUILD repos and 29 popular AUR repos: no high or critical finding on any official package; the only AUR hit is `nvm-git`, a true positive that now stops to ask. End to end against a poisoned upstream (real checkout, scratch `$HOME`, nothing built): a clean PKGBUILD whose helper script writes `authorized_keys` is refused under `--yes --skip-pkgbuild --accept-risks`; a patch adding `curl | sh` is a warning with no extra prompt; a committed ELF and a download-then-run script each stop at the default-no prompt.

Still open: findings are per file (a credential read in one file and an upload in another are not correlated); the manifest of what the *built package* installs needs the build and install steps split and is its own slice.

## Slice u15 — 2026-10-13 — audit

New `emrac audit <target>...` reads a PKGBUILD (and its `install=` scriptlet) for risky code **without running any of it**. A target is an AUR package name (emrac's git checkout is fetched but not advanced; what upstream has now is audited) or a path to a PKGBUILD or its directory — paths need no pacman. It prints findings (rule, severity, `file:line`, message, the line itself) or `--json`, and exits 1 if any target has high or critical findings so scripts can gate on it. The reader (`audit.rs`) understands assignments including multi-line arrays, `declare`/`export` forms and `name[i]=`, functions in all common shapes, quotes, comments, backslash continuations and heredocs (data, not code); a value computed by a command is reported as *dynamic* rather than guessed. Commands are split into pipeline stages and seen through wrappers (`sudo`, `env`, `nohup`, `timeout`, …), so `curl … | sudo bash` and `sudo rm -rf /` are caught.

Severity policy (design owner's decision, `docs/design/source-build.md` §6): **info** and **warning** are only shown; **high** (download piped into a shell, `sudo`, setuid outside the package, `systemctl enable`, reading `~/.ssh` or browser data, LD_PRELOAD, host-changing commands) makes `install`/`upgrade` stop at an `emrac asks:` prompt that defaults to *no* and that `--yes` does **not** answer (`--accept-risks` does); **critical** (writing `.bashrc`/`authorized_keys`/`ld.so.preload`/sudoers, reading credentials *and* sending data out, decode-and-execute, reverse shells, `rm -rf /`-class commands) is **refused by emrac with no override** — the user can still read and build by hand. The audit runs on exactly the PKGBUILD and scriptlet about to be built, on every `install`/`upgrade` of an AUR package, even with `--skip-pkgbuild`/`--skip-diff` and when the checkout is up to date; a refusal happens before the checkout is advanced. Findings go to stderr so structured stdout stays clean. Also flagged as warnings: `http://` sources, `SKIP` checksums on downloads, missing checksums, network use inside `build()`/`check()`/`package()` (the sandbox slice will block it), writes outside `$srcdir`/`$pkgdir`, `eval`, code that runs when the PKGBUILD is merely read. Design in `docs/plan/r1/u15-audit.md`.

Verified with 23 audit unit tests and 2 CLI integration tests (125 core, 10 CLI in total): every rule both ways, wrappers, scriptlets, line numbers, verdicts, JSON, a no-PKGBUILD error. **False-positive survey** over 38 current official-repo PKGBUILDs and 29 popular AUR PKGBUILDs (linux, glibc, openssh, systemd, sudo, firefox, chromium, docker, yay, paru, google-chrome, spotify, …): the first run found real false positives — `empty.sshd` matching `.ssh`, backslash-continued option lines read as commands (`--with-rundir=/run/sudo` as `sudo`), `pacman -T` as a host change, multi-line arrays inside functions and `declare -A` tables read as commands — all fixed at the cause and pinned by regression tests; the final run has **no high or critical findings** on any of the 67. End to end with a poisoned "upstream" behind a real checkout (scratch `$HOME`, nothing built): a critical PKGBUILD is refused under `--yes --skip-pkgbuild --accept-risks` and the checkout stays put; a high one asks, `--yes` and a closed stdin both mean no, `y` continues to the normal review, `--accept-risks` skips only that prompt; a warnings-only one gets no extra prompt.

Limits, stated in the output: pattern rules can miss obfuscation they don't know and can flag legitimate code; extra files in an AUR repo (patches, helper scripts) are not scanned yet; the manifest of what the *built package* installs is u18.

## Slice u13 — 2026-10-13 — pin and unpin

New `emrac pin <pkg>... [--reason TEXT] [--until YYYY-MM-DD]` holds installed packages back from `emrac upgrade`, with an optional note and expiry (from the "holds with reasons and expiry" idea in `ideas.md`, on top of the spec's `pin`/`unpin`). `--until` is the day the hold ends: it is in force until 00:00 UTC of that date. `emrac pin` with no packages lists the pins (expired ones are marked), `emrac unpin <pkg>...` removes them (a name that isn't pinned is an error and nothing is removed), `--json` on the listing. ## Slice u12 — 2026-10-11 — deps, rdeps, why, orphans

Four read-only dependency commands (libalpm only, no root, no network, `--json`), from the spec's Dependency Intelligence group. `emrac deps <pkg> [--recursive]` (alias `depends`) lists a package's required and optional dependencies, each with what satisfies it on this machine (`installed`, `provided by <pkg>` or `not installed`); an uninstalled package is described from the repositories. `--recursive` adds the transitive closure of required dependencies of installed packages, each once with its shallowest level. `emrac rdeps <pkg>` (alias `required-by`) lists installed packages that require it and those that list it as optional. `emrac why <pkg>` says why an installed package is there: explicitly installed (plus who else needs it, capped at 12 names), installed as a dependency with the shortest chain from an explicit package (`bash → readline`; breadth-first over required-by, ties alphabetical, hard dependencies only), or an orphan. `emrac orphans` lists dependencies that nothing requires or optionally depends on, with sizes (the `pacman -Qdtq` rule); it only lists, removal stays with `emrac remove`. Chain and closure searches are pure functions in `deps.rs`. Design in `docs/plan/r1/u12-deps.md`.

Verified with 5 new unit tests (shortest chain, no explicit dependent, cycles, alphabetical ties, closure depths; 96 in emrac-core). On the host: `orphans` equals `pacman -Qdtq` exactly (15 packages), and `rdeps` matches `pacman -Qi`'s "Required By" for readline, glibc and openssl.

## Slice u10 — 2026-10-11 — snapshot and restore

New `emrac snapshot` (alias-free: `snapshot`, `snapshot create [NAME] [--note TEXT]`, `list`, `show <name>`, `delete <name>`) saves the installed package set — name, version, explicit/dependency, official/foreign — as a named restore point, one JSON file each in `~/.local/share/emrac/snapshots`. Names are `[A-Za-z0-9._-]` (they are file names); the default is `snap-N`; an existing name is refused. Everything but `create` works without libalpm. It is a package-set snapshot only: not filesystem snapshots, not config-file contents.

New `emrac restore <name> [--prune]` compares a snapshot with what is installed and plans install (missing), upgrade and downgrade (version differs, compared with libalpm's `vercmp`). Package files are found as rollback finds them (pacman cache, AUR build dir, emrac's archive cache, then the Arch Linux Archive after confirmation; `--offline` skips it); a missing package whose snapshot version is still in the repositories is installed with `pacman -S` instead. Every file that cannot be found is reported in one error before anything is asked or changed. ## Slice u9 — 2026-10-11 — verify

New `emrac verify <pkg>...` (alias `check`) checks that installed files still match what pacman recorded — `pacman -Qkk` with a clearer report and a pointer to `emrac reinstall` for repair. It reads the package's gzip `mtree` from the local db (parsed here with `flate2` and ~60 lines of mtree parsing: `/set`/`/unset` defaults, `\NNN` octal escapes, type/mode/size/sha256/link — libalpm's iterator doesn't expose the digests) and compares each entry with the filesystem under pacman's `RootDir`: missing, wrong type, size, SHA-256 contents, permission bits (incl. setuid/sticky), symlink target. Not checked, on purpose: mtime and owner uid/gid (an unprivileged user can't be expected to match; noisy). Edited `backup=()` config files are reported as "config edited", not as problems (same stance as pacman), though a missing or wrong-mode config file is still a problem. Files an unprivileged user can't read are counted ("couldn't be read — run as root for a complete check") and never treated as damage. The report is printed first; then any real problem makes the command exit 1 with a summary naming the packages and the `emrac reinstall ...` that repairs them, so scripts can use it. Names that aren't installed abort together. Read-only, no root, `--json`, not logged in the history. Design in `docs/plan/r1/u9-verify.md`.

Found while testing in the stock Arch container image, whose `pacman.conf` `NoExtract`s docs, locales and man pages: the mtree describes the whole package, so those files were reported missing. Pacman's `-Qk` skips them, and so does `verify` now — by matching each entry against `pacman-conf NoExtract` (fnmatch-style globs where `*` crosses `/`, `!` re-includes, last match wins, directories matched with a trailing `/`) and by dropping entries absent from libalpm's installed file list.

Verified with 14 new unit tests (mtree parsing incl. defaults/overrides/unset/escapes/links/metadata files, each damage kind against a temp root, clean package, edited vs. missing vs. wrong-mode config, unreadable not a problem, plain and gzip mtree files, NoExtract glob semantics incl. `!` and directories, installed-file-list filtering). Against pacman on the host, over all 1635 installed packages: `verify` flags 8 packages (filesystem, java-runtime-common, libutempter, libvlc, mangowm-git, openssl, spotify, swayosd-git), every one of which `pacman -Qkk` also flags; pacman additionally flags 11 (audit, bind, dbus, libvirt, ollama, openldap, openssh, shadow, stm32cubemx-jre, sudo, systemd), which are exactly the root-only files `verify` reports as "couldn't be read" (e.g. `/etc/sudoers`, `ssh-keysign`) and owner mismatches it deliberately doesn't check (e.g. `/var/lib/ollama` UID/GID). In the podman container with real pacman: a clean install verified ok; after deleting nothing but editing a binary, `chmod 777`, swapping a symlink to `/etc/passwd`, and editing `/etc/nanorc`, `verify` reported the size difference, the permission difference, the symlink difference and the edited config, exited 1 and named `emrac reinstall tree nano`; `--json` carries the issues; `reinstall` fixed everything (the config edit correctly stayed); a `chmod 000` binary was reported as unreadable with exit 0.

Not built: `--all`, mtime/owner checks, signature verification, automatic repair.

## Slice u8 — 2026-10-11 — purge

New `emrac purge <pkg>... [--cascade] [--recursive]`: `emrac remove` with `pacman -Rn`. On Arch the thing `remove` "leaves behind" is the `.pacsave` copy pacman makes of a package's *modified* `backup=()` config files; `purge` deletes them instead. Resolution, `--dry-run`, `--yes` and `--json` are exactly `remove`'s. What's new is the safety net: before anything happens each removed package's config files are checked against the md5 recorded in the local db, and every file that was modified (or couldn't be read — root-only files can't be checked by an unprivileged user, so they are treated as possibly modified) is listed by path and package, with a dedicated `emrac asks:` confirmation separate from the overall one when any exist; `--yes` answers both. Nothing at risk, no extra prompt. `remove` is unchanged and already is the "keep config" behaviour, so the spec's `--keep-config` is not a flag. Files under `$HOME` (pacman has no record of them) and `.pacsave` files left by *earlier* removals (the package is gone from the db) are deliberately not touched. Design in `docs/plan/r1/u8-purge.md`.

Logged as a new `purge` transaction. `undo` reinstalls the packages like it does for a `remove`, and its preview says the deleted configuration files stay deleted.

Verified with 4 new unit tests (config state classification, at-risk rules, hashing against a temp root incl. md5 of a known file / modified / missing, rollback of a purge with its note) and in the podman container with real pacman: `remove` of `nano` with an edited `/etc/nanorc` left `/etc/nanorc.pacsave`; `purge --dry-run` listed the edited file and listed nothing for an unmodified one; declining the second confirmation removed nothing (`nano` and `/etc/nanorc` intact); accepting removed `nano` with no `.pacsave` left; `--yes` did it in one shot; history shows `purge` and `undo --dry-run` shows the note. ## Slice u7 — 2026-10-11 — reinstall

New `emrac reinstall <pkg>...` puts the **installed version** of each named package back (repair a damaged or deleted file, re-run install scripts). It deliberately never reinstalls the repositories' *newer* version: a plain `pacman -S pkg` would turn a reinstall into a partial upgrade, so each package picks a source in order — a package file for exactly the installed version already on disk (`pacman -U`), else the repositories if they still carry that version (`pacman -S`), else the Arch Linux Archive (downloaded after confirmation, then `-U`), and for an AUR package a rebuild (`makepkg -si`) of the existing, already-reviewed checkout, with no new PKGBUILD fetched. If a package can't be had at the installed version the whole command aborts before prompting, naming each package and why (including "the Archive wasn't checked (--offline)"); names that aren't installed are listed together and pointed at `install`. The preview shows each package's source; `--dry-run`, `--yes`, `--json`, `--offline` behave as elsewhere. Build options from the spec (`--source`, `--clean`, `--profile`, ...) need the build system and are not part of this slice. Design in `docs/plan/r1/u7-reinstall.md`.

Logged as a new `reinstall` transaction. Since no version changes, `emrac rollback tx-N` on one is refused with that explanation and a bare `undo` skips reinstall records (it undoes the last transaction that actually changed something).

Verified with 7 new unit tests (source choice for every case incl. the Archive not being consulted unless needed or allowed, rollback refusal, `undo` skipping) and in the podman container with real pacman: deleting `/usr/bin/tree` and reinstalling repaired it from the cached file; after `pacman -Scc` it repaired from the repositories; with an old `tree` installed, the repo ahead and the cache wiped, the reinstall came from the Archive (and `--offline` aborted with the reason instead of upgrading), a multi-package run mixed sources, an unknown name aborted the lot, an AUR package (`downgrade`) whose built files were removed was rebuilt from its checkout, the history shows `reinstall` entries, `undo` targeted the earlier install, and `rollback` refused the reinstall. On the host, read-only: `--dry-run` for repository/file/AUR-without-checkout/unknown cases and `--json`.

## Slice u6 — 2026-10-11 — downgrade

New `emrac downgrade <pkg> [version]` goes back to an older version of an installed package, and `emrac downgrade <pkg> --list` shows what's available (newest first, with whether each version is `local`, `archive` or both, and which is installed). `SPEC.md` lists downgrades as a feature but defines no command, so the shape is new: one package per call; the target must compare older than what's installed (libalpm `vercmp`, so `1.10` > `1.9` and epochs are right) — equal or newer is refused and points at `upgrade`/`install`; without a version it picks the newest version older than the installed one, from the union of files on this machine and the Arch Linux Archive listing (local wins, so nothing is downloaded needlessly). It is the u4/u5 machinery exposed directly: same preview (`downgrade 1 package`, `from 2.3.2-1`, "Will download from the Arch Linux Archive"), `--dry-run`/`--yes`/`--json`/`--offline`, same fetch + signature-checked `sudo pacman -U`, and it is logged as a normal `downgrade` transaction with the previous version recorded — so `emrac undo` reverses it (as an upgrade) and `history` shows it. After success one note says the next `emrac upgrade` will bring the package back and that `IgnorePkg` holds it; emrac does not edit `pacman.conf`. AUR (foreign) packages work from local files only. Design in `docs/plan/r1/u6-downgrade.md`.

Also: package versions are now parsed out of `<name>-<pkgver>-<pkgrel>-<arch>.pkg.tar.*` file names (a pkgver never contains `-`, so `foo` doesn't claim `foo-bar` files; `.sig`/`.part` ignored), shared by the local scan and the Archive listing.

Verified with 6 new unit tests (file-name version parsing, newest-older choice incl. `1.10` vs `1.9` and epochs/pkgrel, nothing-older error, explicit version must be older, merged list order/sources/installed marker). On the host, read-only: `--list` (13 real versions), one-step and explicit `--dry-run`, newer/equal/not-installed refusals, `--offline` with no local older file, `--json`, and nothing written. In the podman container with real pacman: one-step downgrade of `tree` 2.3.2-1 → 2.3.1-1 and an explicit one to 1.8.0-2 (both fetched from the Archive), `undo` of a downgrade upgraded it back, a repeat downgrade then found the file locally with no download section, `--list --offline` showed local files only, an unavailable version was reported, and history shows the chain. A very old `readline` downgrade was rejected by pacman (`invalid or corrupted package (PGP signature)` — the 2020 signing key isn't trusted) and recorded as a `failed` downgrade with nothing installed. Not exercised: pacman refusing a downgrade because a dependent requires the newer version (pacman's own check; the failed-record path is the same one the signature failure used).

Not built: multi-package downgrades, `reinstall`, holding/pinning a package, an interactive version picker.

## Slice u5 — 2026-10-11 — Arch Linux Archive fetch for rollback

`rollback`/`undo`/`redo` no longer need the package file to still be on disk: when a needed official-package version isn't in pacman's cache, the AUR build dir or emrac's own archive cache, it is looked up in the Arch Linux Archive (`archive.archlinux.org`) and downloaded after you confirm. Planning stays free of side effects: it only makes read-only GETs of the package's Archive directory listing, finds the exact `<name>-<version>-<arch>.pkg.tar.*` file (same exact-shape matcher as the local scan; `%3A`-encoded epochs decoded; `.zst` preferred; `.sig` ignored), and the preview gains a "Will download from the Arch Linux Archive" section (also in `--json` as `downloads`). Files land in `~/.cache/emrac/archive/<pkg>/` via a `.part` file renamed on success, are reused by later rollbacks, and the detached `.sig` is fetched beside each package (best effort). AUR packages are never looked up there. `--offline` turns the Archive off entirely, restoring u4's "files missing" abort. A package the Archive doesn't have counts as missing (aggregated, aborts before prompting); an Archive that can't be reached is a hard `Archive` error rather than a claim that the version doesn't exist. Design in `docs/plan/r1/u5-archive-fetch.md`.

Trust: HTTPS plus pacman's own signature check — `pacman -U` verifies the `.sig` beside a file against your keyring. Verified by flipping a byte in a downloaded package: pacman refused it (`invalid or corrupted package (PGP signature)`), nothing was installed and the failure was recorded as a `failed` rollback.

Verified with 9 new unit tests (listing hrefs + percent decoding incl. `%3A`/`%2B`, exact/preferred file selection, URL building and path-injection refusal, and `plan_rollback` using the Archive only for locally-missing official files, never for AUR, never for removals, and surfacing an unreachable Archive) and, read-only on the host, a real listing lookup that produced the download plan and wrote nothing to disk. In the podman container with real pacman: after `pacman -Scc`, `undo --dry-run` showed the download plan, `--offline` aborted naming the file, the real `undo` downloaded `tree 1.8.0-2` (+ `.sig`) and downgraded, `redo` fetched `2.3.2-1` the same way, and a later `undo --dry-run` found the file in the archive cache and showed no download.

Not built: an `emrac downgrade <pkg> [version]` command (it would reuse this), Archive mirrors, resuming partial downloads, progress output.

## Slice u4 — 2026-10-11 — redo

`emrac redo` re-applies the most recent rollback. It is the same code path as `rollback`: reversing a rollback record is a redo, so `rollback_of` now reads as an *active* reversal (a committed rollback that hasn't itself been reversed), and reversing an undo makes the original transaction rollbackable again — undo/redo/undo/redo toggles consistently, and a second `redo` in a row reports there is nothing to redo instead of undoing the first. A downgrade record's inverse is an upgrade (from the newer file the original upgrade left in the pacman cache). `emrac rollback tx-<id of a rollback>` does the same as `redo` for that one. Output reads `redo tx-1 (by reversing tx-2)`; a rollback attempt that failed is neither redoable nor counts as reversing, so re-running `undo` finishes it. Design addendum in `docs/plan/r1/u4-rollback.md`.

Verified with 4 new unit tests (redo of an undo, redo of a downgrade incl. the package-moved-on skip, the undo/redo/undo candidate toggle, failed rollbacks ignored) and in the podman container with real pacman: upgrade → undo (downgrade) → redo (upgrade) → redo again (nothing to redo) → undo → redo, plus install ripgrep → undo → redo; `redo --dry-run` changed nothing; `history` shows the chain.

## Slice u4 — 2026-10-11 — rollback and undo

New `emrac rollback [tx-N]` and `emrac undo` reverse a recorded transaction: an `install` is undone by removing what it installed (`pacman -R`), a `remove` by reinstalling the recorded version, an `upgrade` by downgrading to the previous version (both via `pacman -U` on files already on disk — pacman's `CacheDir` and `~/.cache/emrac/build/<pkg>`; nothing is downloaded). A bare `rollback` and `undo` pick the most recent transaction that is neither a rollback nor already rolled back. Honors `--dry-run`, `--yes` and `--json`.

Safety rules: a package is only touched if it is still as the transaction left it (same version after an install/upgrade, absent after a remove); everything else is listed as left alone with the reason, which also makes rolling back a *failed* transaction reverse exactly the part that landed. If any needed package file is missing the whole rollback aborts before prompting and names every one. Rollbacks are themselves logged (`rollback_of`), `emrac history` shows `rollback of`/`rolled back by`, and rolling back a transaction twice, is refused (reversing a rollback is `redo`, added next). Undoing an install does not cascade: if something now depends on the packages, pacman refuses and the failure is recorded. AUR versions are not compared for the post-state check since RPC metadata can differ from what a VCS package's build produced.

Schema: `PlannedPackage.previous_version` (filled for upgrades) and `TransactionRecord.rollback_of` are new, both optional so u3 logs still parse. Upgrade records written by u3 lack the previous version and are refused with an explanation; old install/remove records work. New `PlanAction::Downgrade`. Design in `docs/plan/r1/u4-rollback.md`.

Verified with 16 new unit tests (inverse for each action, post-state skips, failed-partial, AUR version handling, missing files aggregated, old-format and repeat refusals, candidate ordering, id parsing, exact package-file matching) and inside the podman container with real pacman: upgrade of an Archive-fetched old `tree` then `undo` restored 1.8.0-2 (file found in the AUR build dir); a second `undo` and `rollback tx-1` were refused; `remove` then `rollback` reinstalled from the pacman cache; an `install` of `ripgrep` was undone; rolling back an upgrade whose package was since removed was skipped with a reason; after `pacman -Scc` a rollback aborted naming `tree 2.3.2-1`; `--dry-run` recorded nothing; `history` shows the markers. Not covered by a live test: a rollback of a `failed` transaction (unit-tested only) and `redo`.

## Slice u3 — 2026-10-11 — transaction history

Executed `install`/`remove`/`upgrade` transactions are now recorded in an append-only JSON Lines log at `~/.local/share/emrac/history.jsonl`, and `emrac history` (alias `emrac transactions`, per `SPEC.md`) shows them newest-first with `--limit N`, `--since YYYY-MM-DD` and `--json`. Each record holds an id (`tx-N`), a UTC timestamp, the action, the planned packages, a `committed`/`failed` status and, on failure, the error text. This is groundwork for `rollback`/`undo`/resume, which are not built yet.

Decisions: only transactions that actually ran are logged (dry runs, declined confirmations and empty plans are not); a failed history write only warns on stderr and never changes the transaction's own result; a record is the *plan* that was executed, so a run that failed halfway (official part done, AUR build failed) is one `failed` record rather than per-package status; reading skips unparsable lines so one bad line can't brick the command. Dates use a small tested civil-date conversion instead of adding `chrono`; all times are UTC. Design in `docs/plan/r1/u3-history.md`.

Verified on the host with a scratch `$HOME`: empty history, `--json`, `--limit`, `--since` (including a day with no matches), invalid dates like `2026-02-30` rejected, a hand-written log containing a corrupt line, and `install --dry-run` writing nothing. 10 new unit tests cover the log and date logic.

Verified inside the podman container (real execution): a real `install` and `remove` of `ripgrep` each wrote a `committed` record (`tx-1`, `tx-2`, correct JSON incl. `--json --limit 1`), `remove --dry-run` wrote nothing, and with a stale `/var/lib/pacman/db.lck` forced, `install` failed in `sudo pacman` and wrote a `FAILED` record with the error text while the command still reported its own error. (A removal pacman rejects at the `--print` planning stage, e.g. `remove ncurses`, never executes and so is correctly not recorded.)

Build note: the debug binary was linked against nix's glibc loader because `~/.nix-profile/bin/cargo` precedes `/usr/bin` on this machine's `PATH`, so it can't run in the Arch container or even directly on the host. Build with `PATH=/usr/bin /usr/bin/cargo build` for a binary with the standard `/lib64` loader.

## Slice u1 — 2026-10-11 — config file
